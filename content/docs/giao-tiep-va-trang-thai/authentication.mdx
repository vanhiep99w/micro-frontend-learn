Bạn đăng nhập ở header nhưng remote Account vẫn hiện “Chưa đăng nhập”. Có thể hai app đang giữ hai biến `isLoggedIn` khác nhau. Phát một event login giúp UI đang mở biết thay đổi, nhưng **remote tải sau vẫn cần đọc được phiên hiện tại**.

Bài này áp dụng [snapshot và subscription](/docs/giao-tiep-va-trang-thai/state-ownership) cho session. Cách kết nối là **shell truyền một API phiên qua `mount`**, remote đọc và theo dõi nó. Xác thực người dùng thật vẫn thuộc hệ thống auth/backend; micro-frontend cần phối hợp UI và vòng đời dữ liệu quanh kết quả đó.

<Callout type="warn" title="Ví dụ UI không phải implementation đăng nhập">
  Bài tập JavaScript dùng API giả để thấy luồng truyền dữ liệu và cleanup. Nút chọn user giả không tạo session hợp lệ, không cấp quyền API và tuyệt đối không dùng làm auth production. Phần phía sau giải thích chỗ cần backend/SDK thật.
</Callout>

## Chia sẻ trạng thái phiên chứ không phát token

| Remote cần biết | Không nên cấp tràn lan |
| --- | --- |
| Đang kiểm tra, chưa login, đã login hay chưa xác nhận được | Cookie/session ID, access/refresh token |
| Tên hiển thị và quyền UI tối thiểu cần dùng | Toàn bộ hồ sơ hoặc claims không liên quan |
| Cách yêu cầu login/logout hoặc revalidate | Store nội bộ và logic refresh của từng app |

**Authentication** xác nhận người dùng; **authorization** kiểm tra họ được làm gì. Session snapshot — bản trạng thái phiên để UI đọc — chỉ giúp chọn nội dung hiển thị. Nút đã hiện hoặc biến `authenticated` không thay thế kiểm tra quyền ở backend.

Shell tạo một auth owner — module điều phối phiên — rồi truyền cùng API cho các remote. Không để mỗi app tự tạo auth store và tự refresh credential cạnh tranh nhau.

## Code owner công bố phiên hiện tại

Mẫu dưới nhận `api.getSession()` và `api.logout()`. Với ứng dụng thật, đó là adapter của backend/SDK; ở bài tập, ta thay bằng fixture để không lẫn việc dựng protocol login với việc nối app.

```js title="basic/session.js" sourceFile="basic/session.js" sourceRegion="main"
export function createSession(api) {
  let epoch = 0;
  let snapshot = Object.freeze({ status: 'checking', epoch });
  const listeners = new Set();

  function publish(next) {
    snapshot = Object.freeze(next);
    for (const notify of [...listeners]) notify();
  }

  return {
    getSnapshot: () => snapshot,
    subscribe(notify) {
      listeners.add(notify);
      return () => listeners.delete(notify);
    },
    async revalidate() {
      const started = ++epoch;
      publish({ status: 'checking', epoch });
      try {
        const result = await api.getSession();
        if (started !== epoch) return;
        publish(result.user
          ? { status: 'authenticated', epoch, user: Object.freeze({ ...result.user }) }
          : { status: 'anonymous', epoch });
      } catch {
        if (started === epoch) publish({ status: 'unavailable', epoch });
      }
    },
    async logout() {
      const started = ++epoch;
      publish({ status: 'signing-out', epoch });
      try {
        await api.logout();
        if (started === epoch) publish({ status: 'anonymous', epoch });
      } catch (error) {
        if (started === epoch) publish({ status: 'unavailable', epoch });
        throw error;
      }
    },
  };
}
```

Đọc theo thứ tự của một lần `revalidate()`:

1. Tăng `epoch`, số thứ tự cục bộ để đánh dấu lần kiểm tra/phạm vi đang active.
2. Công bố `checking`: UI chờ, chưa kết luận người dùng là khách.
3. Hỏi API về phiên. Có user thì công bố `authenticated`; không có user thì `anonymous`.
4. Nếu mạng/API lỗi, công bố `unavailable`, **không coi lỗi là chắc chắn đã logout**.
5. Kết quả của epoch cũ không được ghi nữa, ví dụ logout đã bắt đầu trong lúc kiểm tra còn chờ.

Mẫu tăng epoch mỗi lần kiểm tra theo hướng bảo thủ và ẩn UI riêng tư trong lúc đó. SDK thực tế có thể phân biệt refresh cùng phiên với đổi user/tenant, nhưng phải công bố rõ khi nào scope cũ không còn hợp lệ. Các listener demo đồng bộ, không throw; owner production cần chính sách xử lý lỗi subscriber.

## Remote nhận session và shell nối thế nào

### Phía Account đọc snapshot rồi theo dõi

```js title="basic/account.js" sourceFile="basic/account.js" sourceRegion="main"
export function mount({ container, session }) {
  const label = document.createElement('p');
  container.append(label);

  function render() {
    const current = session.getSnapshot();
    switch (current.status) {
      case 'authenticated':
        label.textContent = `Account: ${current.user.displayName}`;
        break;
      case 'anonymous':
        label.textContent = 'Account: chưa đăng nhập';
        break;
      case 'checking':
        label.textContent = 'Account: đang kiểm tra phiên';
        break;
      case 'signing-out':
        label.textContent = 'Account: đang đăng xuất';
        break;
      default:
        label.textContent = 'Account: chưa xác nhận được phiên';
    }
  }

  const unsubscribe = session.subscribe(render);
  render();
  return {
    unmount() { unsubscribe(); label.remove(); },
  };
}
```

Account không đọc token hay đoán login từ localStorage. Nó subscribe rồi render snapshot hiện tại, nên mở sau khi login vẫn thấy đúng user. Unmount chỉ hủy listener của Account, không logout người dùng.

## Nối API thật vào đâu

Với ứng dụng có backend cùng origin, một lựa chọn là **BFF — Backend for Frontend** giữ session/token phía server. Browser gửi cookie; frontend gọi endpoint như `/auth/session` để lấy projection tối thiểu. Tên endpoint là ví dụ, không phải tính năng sẵn có của site docs.

> Playback dưới đây minh họa thứ tự các bước do tác giả chọn; không gửi request thật, không mô phỏng concurrency và tốc độ phát không phải latency. Bạn có thể chạy hoặc xem từng bước.

```d2 title="BFF và cookie session" mode=flow interactive=true
# @flow
# scenarios:
#   - id: session
#     label: "Session đã có token"
#     steps:
#       - edge: "(browser -> bff)[0]"
#         description: "Browser UI → BFF: Cookie session"
#       - edge: "(bff -> api)[0]"
#         description: "BFF → API domain: Access token"
#   - id: refresh
#     label: "Đổi hoặc refresh token"
#     steps:
#       - edge: "(browser -> bff)[0]"
#         description: "Browser UI → BFF: Cookie session"
#       - edge: "(bff -> idp)[0]"
#         description: "BFF → Identity provider: Token exchange / refresh"
#       - edge: "(bff -> api)[0]"
#         description: "BFF → API domain: Access token"
# @endflow
direction: right
browser: Browser UI
bff: BFF
api: API domain
idp: Identity provider
browser -> bff: Cookie session
bff -> api: Access token
bff -> idp: Token exchange / refresh
```

Kịch bản session hợp lệ giả định BFF đã giữ access token. Chỉ khi cần đổi/refresh token, BFF mới gọi IdP trước khi gọi API; token không trả về Browser UI.

Cookie `HttpOnly` không đọc được từ JavaScript, nên remote không cần lấy nó để render. Backend phải cấu hình cookie phù hợp với HTTPS, scope và luồng redirect; endpoint session không được cache công khai. Mutation như logout cần bảo vệ CSRF thực sự ở backend. `HttpOnly` hay `SameSite` riêng lẻ không giải quyết toàn bộ CSRF/XSS.

Nếu browser phải gọi API trực tiếp bằng bearer token, dùng SDK được duy trì với Authorization Code + PKCE theo cấu hình provider. Không đưa client secret vào bundle và không để từng remote tự xử lý cùng callback/refresh. Auth owner hoặc transport giữ credential, chỉ gửi tới API đúng audience/destination; không mặc định lưu token vào localStorage để tiện chia sẻ.

Hai mô hình khác nhau ở chỗ giữ credential, **không bắt remote phải biết token để cùng hiển thị trạng thái phiên**. Public API vẫn có thể là snapshot/subscription và commands.

## Login và logout cần phối hợp những bước nào

### Login không phải chỉ đặt một boolean

1. Remote yêu cầu auth owner bắt đầu login, kèm điểm đến nội bộ hợp lệ.
2. SDK/backend thực hiện redirect/callback và kiểm tra transaction theo protocol.
3. Owner đọc kết quả phiên đã xác nhận rồi công bố snapshot.
4. Shell mở lại điểm đến nếu user được phép; remote tải dữ liệu theo scope mới.

Callback thuộc một owner, không phải mỗi remote xử lý một lần. `returnTo` phải được parse và allowlist ở backend/adapter; `startsWith('/')` chưa đủ vì `//host-khac` có thể đi ra ngoài. Không đưa credential vào URL/event. Mạng lỗi khác với phiên không còn hợp lệ, và `403` thiếu quyền không được biến thành vòng lặp login.

### Logout phải khóa dữ liệu cũ ngay

Ở mẫu nhỏ, `signing-out` ẩn user trước khi chờ API. Trong app thật cần thêm:

- Chặn command riêng tư mới và vô hiệu hóa scope cũ.
- Các domain hủy/bỏ request cũ, dọn cache và draft riêng tư.
- Backend/SDK kết thúc session/revoke theo mô hình thật; cookie `HttpOnly` do backend expire.
- Chỉ báo logout thành công khi có xác nhận. Nếu lỗi mạng, UI vẫn khóa dữ liệu cũ và cho retry.

Xóa state frontend không chứng minh session server đã kết thúc. Logout app cũng không tự logout mọi thiết bị hoặc session SSO ở provider. Không bắt đầu login mới đua với logout chưa xong: epoch chỉ chặn ghi frontend, không chặn `Set-Cookie` từ response network cũ.

## Response cũ không được quay lại phiên mới

Giả sử Cart bắt đầu tải dữ liệu của A, rồi A logout và B login. Response A về sau không được ghi vào UI B. Domain phải ghi nhận epoch lúc bắt đầu và **kiểm tra lại ngay trước khi commit**, cùng user/cart/tenant scope khi có.

`AbortController` giảm công việc thừa, không thay kiểm tra scope. Abort mutation cũng không thu hồi thay đổi đã tới backend. Với API thật, epoch là số cục bộ chứ không phải bằng chứng quyền; backend kiểm tra session và resource độc lập.

<summary>Đối chiếu type session đầy đủ</summary>

```ts
export type SessionUser = Readonly<{
  subject: string;
  displayName: string;
  tenantId: string | null;
  uiPermissions: readonly string[];
}>;

export type SessionSnapshot = Readonly<{ epoch: number }> & (
  | Readonly<{ status: 'checking' }>
  | Readonly<{ status: 'anonymous' }>
  | Readonly<{ status: 'authenticated'; user: SessionUser }>
  | Readonly<{ status: 'signing-out' }>
  | Readonly<{
      status: 'unavailable';
      reason: 'network' | 'server' | 'logout-unconfirmed';
    }>
);

export interface SessionReader {
  getSnapshot(): SessionSnapshot;
  subscribe(listener: () => void): () => void;
}

export type LoginDestination =
  | Readonly<{ kind: 'home' }>
  | Readonly<{ kind: 'cart' }>;

export interface AuthCommands {
  startLogin(destination: LoginDestination): void;
  revalidate(): Promise<void>;
  logout(): Promise<void>;
}

export interface AuthPort extends SessionReader, AuthCommands {}
```

</details>

Mẫu type này mở rộng bài tập bằng user/tenant/UI permissions, destination có cấu trúc và các commands. `Readonly` không tự khóa dữ liệu lúc chạy. Snapshot cần bất biến, giữ reference nếu không đổi và không chứa credential.

```ts
type PrivateView = 'loading' | 'login' | 'content' | 'retry' | 'locked';

export function connectPrivateView(
  session: SessionReader,
  show: (view: PrivateView) => void,
): () => void {
  const update = () => {
    const snapshot = session.getSnapshot();

    switch (snapshot.status) {
      case 'checking':
        show('loading');
        break;
      case 'anonymous':
        show('login');
        break;
      case 'authenticated':
        show('content');
        break;
      case 'unavailable':
        show('retry');
        break;
      case 'signing-out':
        show('locked');
        break;
    }
  };

  const unsubscribe = session.subscribe(update);
  update();
  return unsubscribe;
}
```

<details>
<summary>Helper TypeScript chặn response cart sau khi phiên đổi</summary>

```ts
export type CartDto = Readonly<{
  items: readonly Readonly<{ sku: string; quantity: number }>[];
}>;

export interface CartApi {
  getCart(signal: AbortSignal): Promise<CartDto>;
}

export function loadCartForCurrentSession(
  session: SessionReader,
  api: CartApi,
  commit: (cart: CartDto) => void,
  reportError: (error: unknown) => void,
): () => void {
  const initial = session.getSnapshot();
  if (initial.status !== 'authenticated') return () => {};

  const epoch = initial.epoch;
  const controller = new AbortController();

  const isCurrent = () => {
    const current = session.getSnapshot();
    return !controller.signal.aborted
      && current.status === 'authenticated'
      && current.epoch === epoch;
  };

  const unsubscribe = session.subscribe(() => {
    if (!isCurrent()) controller.abort();
  });

  void (async () => {
    try {
      const cart = await api.getCart(controller.signal);
      if (isCurrent()) commit(cart);
    } catch (error) {
      if (isCurrent()) reportError(error);
    } finally {
      unsubscribe();
    }
  })();

  return () => {
    controller.abort();
    unsubscribe();
  };
}
```

</details>

Các type/helper trên là mẫu thiết kế, không phải implementation backend hay SDK. `loadCartForCurrentSession` giả định adapter đã parse/validate response, cleanup gọi lại an toàn và caller xóa dữ liệu đang hiển thị khi scope đổi. Nó không tự quản lý toàn bộ store hoặc mọi lần đổi route.

## Nhiều tab iframe và standalone

Trong cùng trang, shell truyền object API. **Qua tab hoặc iframe, không còn cùng object memory**, dù UI cùng thuộc một sản phẩm.

| Bối cảnh | Cách phối hợp |
| --- | --- |
| Nhiều tab cùng origin | `BroadcastChannel`/storage notification báo phiên có thể đổi; tab nhận revalidate từ nguồn chuẩn |
| Iframe khác origin | Protocol message có kiểm tra origin/source/schema; luồng auth còn phụ thuộc chính sách cookie/provider |
| Remote chạy độc lập khi phát triển | Adapter dev/test cùng contract hoặc auth thật của môi trường test, không copy credential production |

Message logout có thể khiến tab khác khóa dữ liệu rồi kiểm tra lại. Không broadcast token, user/roles rồi coi payload là bằng chứng đã xác thực. Channel không bảo đảm tab bị suspend nhận đủ thông báo; revalidate khi foreground theo policy.

URL CDN của remote không tạo auth origin riêng nếu code vẫn chạy trong document shell. Iframe thì khác: không mặc định đọc được cookie parent; CORS không vượt qua chính sách third-party cookies. Dùng `targetOrigin` cụ thể và kiểm tra `event.origin`, `event.source` trước khi decode. SSO giữa hai app cũng không có nghĩa hai app có cùng session.

## Những kiểm tra không được bỏ qua

| Thử | Kết quả cần thấy |
| --- | --- |
| Mở remote sau khi login | Đọc được snapshot, không đợi event login kế tiếp |
| Session API lỗi mạng/5xx | UI retry, không kết luận anonymous |
| Logout khi GET cart còn chờ | Dữ liệu bị khóa, response cũ không xuất hiện lại |
| Logout backend thất bại | Không báo thành công giả, dữ liệu riêng tư vẫn khóa |
| API trả 403 | Hiển thị thiếu quyền, không refresh/login vô hạn |
| Nhiều remote gặp credential hết hạn | Auth/transport điều phối renew, không mỗi app tự chạy một luồng |
| SSR hai user cùng lúc | Không dùng mutable session singleton hay cache HTML riêng tư chung |

Single flight là cho các request đủ điều kiện chờ một lần renew chung theo scope; nó không đồng nghĩa tự retry mọi POST. Tác vụ mutation có thể đã chạy khi timeout, cần contract chống trùng backend. Scope ở browser không thay authorization; remote cùng document cũng không phải vùng cách ly với code không đáng tin.
