Team Catalog làm một app sản phẩm bằng React. Team Shell làm app chủ — **shell** — để ghép các phần thành một trang. Catalog được tải vào shell nên ở đây gọi là **remote**. Team Shell cần dùng Catalog mà không phải biết bên trong nó có component nào hay dùng store gì. Hai team cần thống nhất **cách sử dụng app từ bên ngoài**.

Thỏa thuận đó gọi là **contract — hợp đồng giao tiếp**. Trong micro-frontend, nó giúp một team thay đổi code bên trong mà không buộc các team khác sửa theo. Bài này bắt đầu ở ranh giới shell/remote, rồi mới xét API và event giữa các app.

<Callout type="info" title="Phạm vi ví dụ">

</Callout>

## Contract nằm ở ranh giới giữa các app

Giả sử shell tải được file JavaScript của Catalog. Tải thành công mới chỉ có nghĩa là file đã về tới browser. Shell vẫn cần biết:

- Module công bố hàm nào để gắn Catalog vào trang?
- Shell truyền vùng DOM, theme và ngôn ngữ theo cấu trúc nào?
- Khi rời trang, shell gọi gì để tháo Catalog?
- Nếu một bên cập nhật trước, cách gọi cũ còn dùng được không?

Đây mới là phần contract cần giải quyết. Module Federation, import map hoặc một loader có thể giúp lấy module về; chúng không tự định nghĩa các câu trả lời trên.

Ví dụ team Catalog công bố `mount(context)`. Shell chỉ gọi API đó và dùng kết quả trả về. Team Catalog có thể đổi cách quản lý state, tách component hoặc đổi thư viện bên trong, miễn vẫn giữ cách gọi và hành vi đã cam kết.

Trong quan hệ này, Catalog là **provider** — bên cung cấp API mount; shell là **consumer** — bên sử dụng nó. Khi Catalog gọi API giỏ hàng, Catalog lại là consumer. Hai từ này chỉ vai trò trong một lần giao tiếp, không phải hai loại app cố định.

| Thuộc contract công khai | Chi tiết nên để trong remote |
| --- | --- |
| Tên export, input và kết quả của `mount` | Cây component React/Vue |
| Props mà shell được truyền vào | Hook, reducer và cấu trúc store |
| Callback/API mà remote được gọi | Cách chia file và gọi API nội bộ |
| Cách update, cleanup và báo lỗi | DOM bên trong vùng remote sở hữu |

## Shell cần biết gì để gắn một remote

### API mount nhận gì và trả gì

Mẫu dưới đây dùng một API không phụ thuộc React hay Vue. Shell đưa vào vùng DOM; remote tự dùng framework của nó để render bên trong vùng đó. Đây là một cách tích hợp, không phải mọi micro-frontend đều bắt buộc có hàm `mount`: nếu remote export một React component, props và callback của component đó cũng là contract.

```ts title="contracts/catalog-mount.ts" sourceFile="contracts/catalog-mount.ts" sourceRegion="main"
import type { CartCommandsV1 } from './cart-commands';

export type CatalogPropsV1 = Readonly<{
  locale: string;
  currency: string;
  theme: 'light' | 'dark';
}>;

export type CatalogMountContextV1 = Readonly<{
  contract: 'shop.catalog.mount.v1';
  container: HTMLElement;
  props: CatalogPropsV1;
  capabilities: Readonly<{
    cart: CartCommandsV1;
  }>;
}>;

export type CatalogHandleV1 = Readonly<{
  updateProps(next: CatalogPropsV1): void;
  unmount(): void;
}>;

export interface CatalogRemoteV1 {
  mount(context: CatalogMountContextV1): CatalogHandleV1;
}
```

Đọc theo ba nhóm, không cần nhớ mọi tên type:

1. **`props` là dữ liệu hiển thị:** locale, currency và theme. Đây không phải store dùng chung.
2. **`capabilities.cart` là chức năng được cấp:** Catalog được gọi API giỏ hàng qua object này. Shell không đưa toàn bộ state của mình cho remote.
3. **`CatalogHandleV1` là cách điều khiển app sau khi gắn:** shell có thể cập nhật props hoặc tháo app.

`CartCommandsV1` mô tả hàm thêm hàng, được giải thích ở phần tiếp theo. Hậu tố `V1` là tên phiên bản của API mẫu, không phải phiên bản React hay số lần deploy của Catalog.

### Đọc một lần gọi từ shell

Giả sử loader đã lấy được module Catalog đúng API. Hàm dưới chỉ thực hiện phần **nối remote với trang**, không thực hiện việc tải module:

```ts title="shell/catalog-slot.ts" sourceFile="shell/catalog-slot.ts" sourceRegion="main"
import type { CartCommandsV1 } from '../contracts/cart-commands';
import type {
  CatalogHandleV1,
  CatalogRemoteV1,
} from '../contracts/catalog-mount';

export function attachCatalog(
  remote: CatalogRemoteV1,
  container: HTMLElement,
  cart: CartCommandsV1,
): CatalogHandleV1 {
  return remote.mount({
    contract: 'shop.catalog.mount.v1',
    container,
    props: {
      locale: 'vi-VN',
      currency: 'VND',
      theme: 'light',
    },
    capabilities: { cart },
  });
}
```

`container` là vùng trang shell dành cho Catalog. `cart` là API giỏ hàng đã được khởi tạo, có thể dùng ngay cả khi màn hình giỏ hàng chưa mở. Object trả về là handle của đúng instance Catalog vừa gắn.

Shell gọi `handle.updateProps(...)` khi cấu hình đổi, và `handle.unmount()` khi rời vùng trang đó. Shell không cần tìm nút bấm, gọi hook hoặc sửa store bên trong Catalog.

Sơ đồ dưới phân biệt **bên nối app** với **bên cung cấp chức năng**. Các mũi tên không phải request HTTP:

```d2 interactive=false title="Shell truyền API công khai vào remote"
direction: down
shell: "Shell"
catalog: "Catalog remote"
cart: "API giỏ hàng"
shell -> catalog: "Mount với context"
catalog -> cart: "Gọi addItem"
```

Cách nối này có một giới hạn rõ: shell biết các API cần thiết để ghép trang, nhưng không phải nơi chứa mọi nghiệp vụ của các remote.

### Update và unmount phải có quy tắc rõ

Chỉ ghi `unmount(): void` chưa đủ để hai team dùng được nhau. Với mẫu này, hai bên cam kết:

| Thao tác | Quy tắc |
| --- | --- |
| `mount` | Chỉ gắn vào container chưa có instance Catalog hoạt động; remote chỉ quản lý DOM bên trong container đó |
| `updateProps` | Nhận toàn bộ props mới; đổi theme/ngôn ngữ không xóa nội dung người dùng đang nhập |
| Đổi API cart hoặc đổi tài khoản | Shell unmount instance cũ rồi mount với context mới |
| `unmount` | Dọn UI, listener, timer và subscription do instance tạo; gọi lại vẫn an toàn |
| `updateProps` sau unmount | Báo lỗi lập trình, không tự dựng lại app |
| `mount` lỗi giữa chừng | Remote dọn tài nguyên đã tạo trước khi throw; shell bắt lỗi và hiện thông báo thay thế |

Đây là lựa chọn của mẫu thiết kế, không phải quy tắc bắt buộc cho mọi micro-frontend. Điều quan trọng là shell và remote thực hiện **cùng một quy ước**. Ví dụ shell tưởng update chỉ đổi theme, nhưng remote lại reset toàn bộ form, thì type vẫn đúng mà tích hợp vẫn sai.

## Remote gọi chức năng của app khác qua đâu

Catalog có nút “Thêm vào giỏ”, nhưng team Cart chịu trách nhiệm quản lý giỏ. Catalog không nên import `cart/internal/store` để tự sửa dữ liệu. Nó chỉ cần gọi hàm công khai đã nhận trong `capabilities.cart`.

Ví dụ, bên trong Catalog có thể gọi:

```ts
const result = await context.capabilities.cart.addItem(
  { cartId: 'cart-demo', productId: 'mug', quantity: 1 },
  { operationId: 'operation-demo-001' },
);
```

Lợi ích đối với micro-frontend là **Catalog biết cách yêu cầu, không biết cách Cart triển khai**. Team Cart có thể đổi thư viện cache hoặc store mà giữ nguyên cách gọi này.

Object đầu nói cần làm gì: thêm một sản phẩm vào giỏ nào, số lượng bao nhiêu. Object thứ hai chứa ID của thao tác để theo dõi và xử lý việc gửi lại nếu cần. Khi người dùng thực hiện một thao tác mới, ứng dụng phải tạo ID mới; chuỗi cố định trên chỉ để minh họa.

### Thiết kế command và kết quả

Hàm yêu cầu thay đổi như `addItem` thường gọi là **command**. Contract cần nói input là gì và bên gọi nhận lại kết quả nào, thay vì chỉ ghi “gửi một event thêm hàng”.

Trong mẫu này, `quantity` là lượng muốn thêm, không phải tổng lượng sau cùng. `snapshot` là dữ liệu giỏ tại một thời điểm đã xác nhận. `revision` là số phiên bản dữ liệu tăng khi giỏ thay đổi; chỉ so sánh revision trong cùng giỏ.

| Kết quả | Catalog hiểu và xử lý thế nào? |
| --- | --- |
| `committed` | Thêm hàng đã được xác nhận; hiển thị thành công |
| `rejected` | Không áp dụng thao tác; hiển thị lỗi theo `code` |
| `unknown` | Chưa biết thao tác đã được áp dụng hay chưa; chuyển sang kiểm tra kết quả, không tự thêm một lần mới |

<details>
<summary>Xem type đầy đủ của API thêm hàng</summary>

```ts title="contracts/cart-commands.ts" sourceFile="contracts/cart-commands.ts" sourceRegion="main"
export type CartSnapshotV1 = Readonly<{
  cartId: string;
  revision: number;
  itemCount: number;
}>;

export type AddItemInputV1 = Readonly<{
  cartId: string;
  productId: string;
  quantity: number;
}>;

export type AddItemResultV1 =
  | Readonly<{
      status: 'committed';
      snapshot: CartSnapshotV1;
    }>
  | Readonly<{
      status: 'rejected';
      code: 'INVALID_QUANTITY' | 'OUT_OF_STOCK' | 'FORBIDDEN';
    }>
  | Readonly<{
      status: 'unknown';
      operationId: string;
    }>;

export interface CartCommandsV1 {
  addItem(
    input: AddItemInputV1,
    options: Readonly<{
      operationId: string;
      signal?: AbortSignal;
    }>,
  ): Promise<AddItemResultV1>;
}
```

</details>

Tại sao không chỉ trả `true` hoặc `false`? Ví dụ request đã gửi nhưng bị timeout: server có thể đã xử lý, chỉ có phản hồi không tới browser. Nếu Catalog hiểu mọi lỗi là “chưa thêm” rồi gửi lại như thao tác mới, người dùng có thể bị thêm hai lần.

`operationId` nhận diện một ý định thao tác; nếu gửi lại đúng ý định đó thì giữ cùng ID và input. Chống áp dụng trùng cần backend hỗ trợ, không tự có nhờ khai báo TypeScript. Consumer vẫn cần `catch` cho lỗi ngoài các kết quả đã mô hình hóa; hủy chờ bằng `AbortSignal` cũng không thu hồi thao tác đã xử lý ở server.

Ở mức micro-frontend, điều cần chốt là: **bên cung cấp phải nói rõ kết quả và lỗi; bên dùng không phải đoán cách xử lý từ implementation nội bộ**. Phần kiểm chứng các nhánh này nằm trong [Contract tests](/docs/kiem-thu-va-tooling/contract-tests).

## Event giữa các app cũng là contract

Nếu Cart muốn thông báo cho header và các app khác rằng giỏ đã đổi, có thể phát event. Khác với lời gọi `addItem`, bên phát không chờ từng UI nhận event để xác nhận thêm hàng thành công.

Ví dụ event dùng trong nhóm bài này:

```json
{
  "type": "shop.cart.updated.v1",
  "eventId": "event-demo-001",
  "source": "cart",
  "occurredAt": "2026-03-01T08:00:00.000Z",
  "correlationId": "operation-demo-001",
  "payload": {
    "cartId": "cart-demo",
    "revision": 42,
    "itemCount": 3
  }
}
```

Bên nhận cần biết ba điều, không chỉ tên các field:

- **Dữ liệu nói gì?** `itemCount` là tổng số lượng hiện tại, không phải số cần cộng thêm. `revision` dùng phân biệt dữ liệu cũ/mới trong cùng giỏ.
- **Thông báo nào đang được xử lý?** `eventId` nhận diện event; `correlationId` nối nó với thao tác liên quan. `source` và `occurredAt` phục vụ truy vết, không chứng minh danh tính hay thay revision để sắp thứ tự dữ liệu.
- **Nếu app chưa mở thì sao?** Bus trong bộ nhớ của ví dụ không lưu lịch sử. App mở sau phải đọc dữ liệu hiện tại từ API giỏ hàng, không chờ event cũ được phát lại.

Vì vậy, event contract còn bao gồm thời điểm phát, việc có lưu/phát lại hay không và cách xử lý event lặp. Giữ nguyên JSON nhưng đổi cách chuyển thông báo cũng có thể làm app nhận hoạt động sai. Xem [Events và message bus](/docs/giao-tiep-va-trang-thai/events) cho phần cài đặt.

## Đổi phiên bản mà không buộc mọi app deploy cùng

Đây là lý do contract đặc biệt quan trọng với micro-frontend. Khi team Catalog phát hành remote mới, không thể giả định mọi shell trong browser cũng đã cập nhật.

Ví dụ shell cũ đang gọi `mount(context)` theo v1. Remote mới yêu cầu thêm `tenantId` bắt buộc trong context, nhưng shell cũ không gửi. Remote mới có thể chạy tốt khi test riêng và vẫn hỏng khi ghép vào trang thật.

| Thay đổi | Ảnh hưởng tới bên đang dùng |
| --- | --- |
| Catalog đổi store bên trong, API giữ nguyên | Không cần bắt shell sửa theo |
| Thêm prop tùy chọn, có mặc định giữ hành vi cũ khi thiếu | Có thể tương thích nếu cả hai chiều đều được kiểm tra |
| Thêm input bắt buộc | Bên gọi cũ thiếu input; không còn dùng đúng cách cũ |
| Đổi `unmount` thành `destroy` và bỏ tên cũ | Shell cũ không còn tháo app được |
| Giữ tên `updateProps` nhưng bắt đầu reset form | Hành vi cũ bị phá dù chữ ký TypeScript không đổi |
| Đổi ý nghĩa hoặc loại dữ liệu của field event | App nghe theo cách cũ có thể hiển thị sai |

Thay đổi làm bên dùng theo cam kết cũ không còn hoạt động đúng gọi là **breaking change**. Khi cần thay đổi như vậy, hãy công bố API mới và có giai đoạn giữ API cũ, thay vì âm thầm sửa nghĩa v1.

Một trình tự có thể áp dụng cho mount API:

1. Remote hỗ trợ cả cách gọi v1 và v2 trong giai đoạn chuyển tiếp.
2. Shell mới dùng v2 khi đã xác định remote hỗ trợ; vẫn có cách dùng v1 nếu phải chạy với remote cũ.
3. Test shell cũ/remote mới và shell mới/remote cũ, kể cả khi rollback.
4. Chỉ gỡ v1 sau khi các consumer và bản rollback còn được hỗ trợ không cần nó nữa.

Tên `V1` trong type không tự kiểm tra bước 2. Ứng dụng cần một cách chọn API lúc chạy, chẳng hạn export/descriptor công bố rõ phiên bản mà remote hỗ trợ. Nếu thiếu API bắt buộc, shell không mount và hiển thị thông báo thay thế. Loader phải kiểm tra khai báo và export thực tế; không chỉ tin một bản type ở lúc build.

Cũng cần phân biệt: **version package types**, **version API** và **version build remote** là ba thứ khác nhau. Nâng package `@shop/contracts` không tự buộc tab browser tải đúng build remote; đổi build cũng không nhất thiết đổi API.

## TypeScript không thay được kiểm tra lúc chạy

Shell có thể build bằng types v1 nhưng tải một remote khác phiên bản khi người dùng mở trang. Vì thế, typecheck chỉ kiểm tra phần code và khai báo đã có lúc build, không bảo đảm module tải về giữ đúng lời hứa.

Ở ranh giới tải remote, hãy kiểm tra export cần dùng và phiên bản API hỗ trợ. Ở ranh giới message/event, hãy kiểm tra dữ liệu nhận được trước khi dùng. Ví dụ:

```ts
const snapshot = JSON.parse(text) as CartSnapshotV1;
```

Dòng này không kiểm tra JSON có đúng snapshot hay không. `as` chỉ nói với compiler “hãy coi nó là type này”; `itemCount: "3"` vẫn có thể lọt qua khi chạy.

Bước kiểm tra lúc chạy gọi là **runtime validation**. Với event không hợp lệ, bỏ thông báo và ghi nhận lỗi; không biến nó thành một giỏ rỗng để che lỗi. Schema/decoder mẫu nằm ở phần tra cứu cuối bài.

Một package contract dùng chung có thể chứa type, quy tắc hành vi, schema và dữ liệu mẫu cho test. Không cần nhét store hoặc React Context đang giữ state vào package đó. Chia sẻ thỏa thuận không đồng nghĩa với chia sẻ toàn bộ implementation.

<Callout type="warn" title="Contract không phải ranh giới bảo mật">
  Kiểm tra cấu trúc dữ liệu không chứng minh bên gửi có quyền thực hiện thao tác. Các remote cùng trang cũng không tự được cách ly bảo mật. Với iframe, kiểm tra origin/source trước khi decode message và chỉ gửi đến targetOrigin phù hợp; backend vẫn phải kiểm tra quyền độc lập.
</Callout>

## Kiểm thử những gì ở ranh giới

Test contract nên quan sát thứ bên ngoài được phép dùng. Nếu test phải đọc reducer, hook hoặc DOM nội bộ không công bố, nó đang kiểm tra implementation chứ chưa bảo vệ tốt ranh giới giữa các app.

| Ranh giới | Điều cần kiểm tra |
| --- | --- |
| Shell gọi remote | Export mount thật nhận context hợp lệ, trả handle có API đã công bố |
| Remote render | Chỉ tác động vào container được giao, không sửa phần bên cạnh |
| Update cấu hình | Theme/ngôn ngữ đổi nhưng draft người dùng không bị xóa ngoài cam kết |
| Tháo app | Unmount lặp an toàn, không còn listener/timer do instance cũ tạo |
| Gọi chức năng app khác | Input và kết quả đúng contract; có nhánh xử lý lỗi |
| Nhận event | Từ chối dữ liệu sai, xử lý event lặp theo quy tắc đã công bố |
| Phát hành độc lập | Các tổ hợp consumer/provider cũ và mới được hỗ trợ vẫn hoạt động |

Chạy test với export thật của provider, không chỉ với một mock luôn trả kết quả đúng. Khi đổi remote, phần quan trọng là chứng minh **consumer đang dùng API công khai vẫn hoạt động**, không phải chứng minh mọi dòng code bên trong giữ nguyên.

## Mẫu kiểm tra dữ liệu để tra cứu

Phần này giữ các file mẫu đầy đủ cho người triển khai. Bạn có thể bỏ qua ở lần đọc đầu; chúng không phải điều kiện để hiểu cách shell và remote kết nối ở trên.

### Decoder kiểm tra một snapshot

Decoder là hàm nhận dữ liệu chưa tin cậy, kiểm tra nó rồi trả dữ liệu đã hợp lệ. Mẫu này kiểm tra riêng snapshot, không kiểm tra toàn bộ event:

<details>
<summary>Xem contracts/decode-cart-snapshot.ts</summary>

```ts title="contracts/decode-cart-snapshot.ts" sourceFile="contracts/decode-cart-snapshot.ts" sourceRegion="main"
import type { CartSnapshotV1 } from './cart-commands';

function isRecord(value: unknown): value is Record<string, unknown> {
  return typeof value === 'object'
    && value !== null
    && !Array.isArray(value);
}

function isId(value: unknown): value is string {
  return typeof value === 'string'
    && value.length <= 200
    && value.trim().length > 0;
}

function isCount(value: unknown): value is number {
  return typeof value === 'number'
    && Number.isSafeInteger(value)
    && value >= 0;
}

export function decodeCartSnapshotV1(value: unknown): CartSnapshotV1 {
  if (!isRecord(value)
    || !isId(value.cartId)
    || !isCount(value.revision)
    || !isCount(value.itemCount)) {
    throw new TypeError('Invalid cart snapshot v1');
  }

  // Copy các field public: không giữ reference tới object của publisher.
  return Object.freeze({
    cartId: value.cartId,
    revision: value.revision,
    itemCount: value.itemCount,
  });
}
```

</details>

Hàm từ chối ID rỗng, số âm, số thập phân và số vượt giới hạn nguyên an toàn của JavaScript. Nó không tự sửa chuỗi `"3"` thành số `3`. Object trả về là bản copy chỉ có field v1, được khóa bằng `Object.freeze`; object gốc thay đổi không làm snapshot đã đọc đổi theo.

### Schema kiểm tra ở runtime

JSON Schema là cách mô tả quy tắc dữ liệu để một validator kiểm tra. File dưới dùng Draft 2020-12 và kiểm tra cả thông tin event lẫn payload. ID dài tối đa 200 ký tự là giới hạn minh họa của mẫu, không phải chuẩn micro-frontend.

<details>
<summary>Xem schema đầy đủ cho shop.cart.updated.v1</summary>

```json title="contracts/cart-updated.v1.schema.json" sourceFile="contracts/cart-updated.v1.schema.json" sourceRegion="main"
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "title": "Shop cart updated v1",
  "type": "object",
  "required": [
    "type", "eventId", "source", "occurredAt", "correlationId", "payload"
  ],
  "properties": {
    "type": { "const": "shop.cart.updated.v1" },
    "eventId": { "$ref": "#/$defs/id" },
    "source": { "const": "cart" },
    "occurredAt": { "type": "string", "format": "date-time" },
    "correlationId": { "$ref": "#/$defs/id" },
    "payload": {
      "type": "object",
      "required": ["cartId", "revision", "itemCount"],
      "properties": {
        "cartId": { "$ref": "#/$defs/id" },
        "revision": { "$ref": "#/$defs/count" },
        "itemCount": { "$ref": "#/$defs/count" }
      },
      "additionalProperties": true
    }
  },
  "additionalProperties": true,
  "$defs": {
    "id": {
      "type": "string",
      "minLength": 1,
      "maxLength": 200,
      "pattern": "\\S"
    },
    "count": {
      "type": "integer",
      "minimum": 0,
      "maximum": 9007199254740991
    }
  }
}
```

</details>

`required` chỉ rõ field bắt buộc; `additionalProperties: true` cho phép event có field bổ sung mà vẫn giữ field v1 hợp lệ. Cho phép field mới không có nghĩa là chấp nhận đổi nghĩa hoặc đổi type field cũ. Đừng áp dụng máy móc quy tắc bỏ qua field mới cho command nếu field đó thay đổi yêu cầu nghiệp vụ.

Validator phải hỗ trợ đúng draft và được cấu hình kiểm tra `format: date-time` nếu muốn từ chối timestamp sai. Có file schema chưa có nghĩa là ứng dụng đã chạy bước validation.

### Test decoder

Mẫu test sau kiểm tra phần dữ liệu công khai, không cần truy cập store của remote. Chạy sau khi compile TypeScript hoặc bằng runner hỗ trợ TypeScript:

<details>
<summary>Xem test các trường hợp hợp lệ và không hợp lệ</summary>

```ts title="contracts/decode-cart-snapshot.test.ts" sourceFile="contracts/decode-cart-snapshot.test.ts" sourceRegion="main"
import assert from 'node:assert/strict';
import { decodeCartSnapshotV1 } from './decode-cart-snapshot';

const oldFixture = {
  cartId: 'cart-demo',
  revision: 42,
  itemCount: 3,
};

assert.deepEqual(decodeCartSnapshotV1(oldFixture), oldFixture);

// Output mới bổ sung field không phá consumer chỉ cần projection v1.
assert.deepEqual(
  decodeCartSnapshotV1({ ...oldFixture, lineCount: 2 }),
  oldFixture,
);

for (const invalid of [
  { ...oldFixture, itemCount: '3' },
  { ...oldFixture, itemCount: -1 },
  { ...oldFixture, revision: Number.MAX_SAFE_INTEGER + 1 },
  { ...oldFixture, cartId: '   ' },
  { cartId: 'cart-demo', revision: 42 },
  null,
  [],
]) {
  assert.throws(() => decodeCartSnapshotV1(invalid), TypeError);
}

const raw = { ...oldFixture };
const decoded = decodeCartSnapshotV1(raw);
raw.itemCount = 99;
assert.equal(decoded.itemCount, 3);
assert.equal(Object.isFrozen(decoded), true);
```

</details>

Test decoder chỉ chứng minh dữ liệu được kiểm tra đúng quy tắc. Nó không chứng minh API thật tính đúng số lượng, cleanup đúng hoặc hai build remote tương thích. Các kiểm tra đó cần chạy với implementation và tổ hợp phiên bản tương ứng.
