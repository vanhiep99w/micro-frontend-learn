Giả sử cart vừa deploy và đổi `itemCount` từ tổng quantity sang số dòng sản phẩm. Shell vẫn đọc một `number`, TypeScript vẫn build thành công, nhưng badge bỗng hiển thị sai. Một thay đổi khác dễ thấy hơn: catalog bắt đầu gửi field bắt buộc mới trong command, trong khi cart mà người dùng đang mở vẫn là bản cũ.

Để các micro-frontend deploy độc lập, bạn cần thống nhất nhiều hơn tên field và type. **Contract phải nói rõ dữ liệu có nghĩa gì, ai được gọi, kết quả được bảo đảm đến đâu và phiên bản nào dùng được với nhau.** Bài này giúp bạn thiết kế boundary đó trước khi chọn transport hoặc thư viện chia sẻ state.

<Callout type="info" title="Phạm vi ví dụ">
  Bài dùng shop giả định gồm shell, catalog và cart, nối tiếp ví dụ trong các trang events và state ownership. Code TypeScript, tên package và đường dẫn bên dưới là mẫu thiết kế, không phải implementation có sẵn trong repository docs. Functions và DOM element chỉ dùng cho các remote cùng JavaScript realm; dữ liệu đi qua iframe cần protocol message riêng.
</Callout>

## Contract không chỉ là interface

Contract là cam kết công khai giữa bên cung cấp và bên sử dụng một boundary. Nó giống một mẫu phiếu giao hàng: người gửi và người nhận thống nhất phải điền gì, từng ô có nghĩa gì, và khi phiếu không hợp lệ thì xử lý thế nào. Điểm khác là các remote có thể giữ những phiên bản mẫu khác nhau trong cùng một phiên browser; vì vậy, tương thích phải được thiết kế chứ không thể chỉ dựa vào việc hai team đã thống nhất một lần.

Một interface như `{ itemCount: number }` mô tả shape, nhưng không trả lời `0` có nghĩa là giỏ rỗng hay chưa tải. Nó cũng không nói con số là tổng quantity hay số SKU khác nhau. Khi hai bên tự suy đoán khác nhau, dữ liệu đúng type vẫn tạo UI sai.

### Những gì cần ghi trong contract

| Phần | Câu hỏi phải trả lời | Ví dụ với cart |
| --- | --- | --- |
| Owner | Ai quyết định semantics và duyệt thay đổi? | Cart domain sở hữu cart command và cart events |
| Consumer | Ai cần boundary này, cần quyền gì? | Catalog gửi command; shell chỉ đọc summary |
| Shape | Field nào bắt buộc, optional, nullable? | `itemCount` là số nguyên không âm khi dữ liệu đã xác nhận |
| Semantics | Đơn vị, phạm vi và nguồn chuẩn là gì? | `itemCount` là tổng quantity của một `cartId` |
| Lifecycle | Khi nào gọi được, khi nào hết hiệu lực? | Capability sống theo session, không theo route cart |
| Delivery | Có lưu lịch sử, ACK hoặc retry không? | Bus trong memory không replay cho subscriber đến muộn |
| Failure | Kết quả nào là lỗi nghiệp vụ, lỗi nào chưa biết? | Timeout không chứng minh backend chưa commit |
| Compatibility | Consumer và provider nào được ghép? | Consumer v1 tiếp tục hoạt động với provider còn hỗ trợ v1 |
| Security | Ai authorize, dữ liệu nào không được truyền? | Backend kiểm tra quyền; không gửi token qua event |
| Migration | Khi nào ngừng hỗ trợ và rollback thế nào? | Giữ v1 trong cửa sổ chuyển tiếp đã công bố |

Không phải mọi contract đều cần nhiều trang mô tả. Với một capability nhỏ, một interface, bảng semantics và vài fixture có thể đủ. Nhưng đừng bỏ các quy tắc hành vi chỉ vì chúng không biểu diễn được trong TypeScript.

### Public boundary và implementation nội bộ

Mình mặc định công bố contract theo domain, không theo thư viện đang dùng. Catalog cần `addItem`, không cần reducer, store instance hay query key nội bộ của cart.

```text
Catalog ── command contract ──► Cart domain ──► Backend
Shell   ◄── summary / event ─── Cart domain

Shell ── mount context + capabilities ──► Catalog remote
```

Shell wiring các capability vào remote; cart domain vẫn sở hữu ý nghĩa của mutation. Nếu đổi cart từ Redux sang một controller khác mà catalog phải sửa import, boundary đang lộ implementation.

Không cần tạo public contract cho mọi helper nội bộ. Các component cùng owner và cùng vòng release có thể chia sẻ code trực tiếp; contract có version hữu ích nhất ở ranh giới mà hai bên thật sự cần tiến hóa độc lập.

## Chọn hình thức giao tiếp

| Nhu cầu | Lựa chọn mặc định | Contract cần mô tả |
| --- | --- | --- |
| Container truyền cấu hình hiển thị | Props hoặc mount context | Giá trị ban đầu, update, default và phạm vi hiệu lực |
| Consumer yêu cầu owner làm việc và cần kết quả | Function capability hoặc request-response API | Input, result, lỗi, cancellation và retry |
| Owner thông báo một thay đổi đã xảy ra | Event | Envelope, payload, delivery và cách lấy snapshot hiện tại |
| Consumer cần dữ liệu khi mount muộn | Query hoặc read-only snapshot API | Loading/error, freshness, scope và revision nếu có |
| Shell nói chuyện với iframe | Message protocol qua `postMessage` | Schema serializable, request ID, handshake, origin/source validation |

Props phù hợp với mối quan hệ container–remote. Event phù hợp khi publisher không cần biết subscriber nào đang tồn tại. Với thao tác “thêm sản phẩm và cho biết kết quả”, mình chọn capability thay vì phát một event `add-item` rồi chờ một event khác không có timeout rõ ràng.

Cùng một domain có thể công bố nhiều boundary. Cart nhận command, trả snapshot và phát notification; ba phần đó bổ sung cho nhau chứ không phải ba lựa chọn loại trừ nhau.

<Callout type="warn" title="Transport không thay thế contract">
  Module Federation quyết định cách tải module, không tự bảo đảm payload tương thích. `CustomEvent` truyền dữ liệu, không định nghĩa ownership. `postMessage` đưa message tới context khác, không tự authorize nội dung message.
</Callout>

## Thiết kế props và lifecycle

### Mount contract cho catalog

Một remote độc lập framework có thể expose `mount` thay vì buộc shell import React component. Ví dụ này dùng `productId` làm ID sản phẩm thống nhất với trang events; nếu ứng dụng dùng SKU, hãy công bố rõ loại định danh thay vì coi hai tên là tương đương.

```ts title="contracts/catalog-mount.ts"
import type { CartCommandsV1 } from './cart-commands';

export type CatalogPropsV1 = Readonly<{
  locale: string;
  currency: string;
  theme: 'light' | 'dark';
}>;

export type CatalogMountContextV1 = Readonly<{
  contract: 'shop.catalog.mount.v1';
  container: HTMLElement;
  props: CatalogPropsV1;
  capabilities: Readonly<{
    cart: CartCommandsV1;
  }>;
}>;

export type CatalogHandleV1 = Readonly<{
  updateProps(next: CatalogPropsV1): void;
  unmount(): void;
}>;

export interface CatalogRemoteV1 {
  mount(context: CatalogMountContextV1): CatalogHandleV1;
}
```

`locale` là language tag mà provider hỗ trợ, còn `currency` là mã tiền tệ mà UI hỗ trợ; `string` không có nghĩa mọi chuỗi đều hợp lệ. Contract thật cần công bố tập giá trị hoặc chính sách fallback. `currency` ở props chỉ là cấu hình hiển thị, không cho catalog tự đổi tiền tệ của giỏ hàng đã được backend xác nhận.

Context truyền một capability nhỏ, không truyền toàn bộ shell service container. Nhờ vậy, test catalog chỉ cần mock command cart, không cần dựng toàn bộ platform.

### Quy tắc cập nhật và cleanup

Interface trên đi kèm các quy tắc sau:

- `mount` chỉ gọi khi container chưa có instance đang hoạt động của remote này; remote chỉ sở hữu DOM bên trong container.
- `updateProps` nhận **toàn bộ props mới**, không phải partial patch. Remote cập nhật locale, currency và theme mà không remount; draft và state tương tác không liên quan được giữ lại.
- Capability có identity ổn định trong lifecycle mount. Nếu cần thay session hoặc thay capability, shell unmount rồi mount context mới theo policy này.
- `unmount` có thể gọi nhiều lần và phải cleanup listener, timer, subscription và DOM do instance tạo. `updateProps` sau unmount bị từ chối bằng lỗi lập trình, không âm thầm dựng lại UI.
- Nếu `mount` throw, implementation phải cleanup phần đã tạo trước khi throw; shell hiển thị fallback và không gọi `unmount` trên handle chưa tồn tại.

Đây là lựa chọn cho ví dụ, không phải chuẩn bắt buộc của mọi micro-frontend. Bạn có thể dùng mount bất đồng bộ, partial update hoặc một hàm `updateContext`, nhưng phải công bố hành vi tương ứng và test nó.

Có cleanup UI không đồng nghĩa mutation backend đã bị hủy. Remote cần ngăn response muộn cập nhật instance đã unmount hoặc session cũ; nếu command đã gửi tới backend, owner vẫn phải reconcile kết quả theo contract command.

<Callout type="info" title="Functions không phải wire data">
  `HTMLElement` và function capability không truyền được như dữ liệu qua `postMessage`. Với iframe, chuyển mount/config thành message serializable và xây request-response adapter cho command. Đừng cố serialize object context này hoặc coi một cast TypeScript là bridge.
</Callout>

## Thiết kế command và kết quả

### Capability thêm sản phẩm

Catalog không nên có quyền `setCartState`. Nó chỉ cần yêu cầu thêm một sản phẩm, còn cart domain quyết định gọi backend và cập nhật state thế nào.

```ts title="contracts/cart-commands.ts"
export type CartSnapshotV1 = Readonly<{
  cartId: string;
  revision: number;
  itemCount: number;
}>;

export type AddItemInputV1 = Readonly<{
  cartId: string;
  productId: string;
  quantity: number;
}>;

export type AddItemResultV1 =
  | Readonly<{
      status: 'committed';
      snapshot: CartSnapshotV1;
    }>
  | Readonly<{
      status: 'rejected';
      code: 'INVALID_QUANTITY' | 'OUT_OF_STOCK' | 'FORBIDDEN';
    }>
  | Readonly<{
      status: 'unknown';
      operationId: string;
    }>;

export interface CartCommandsV1 {
  addItem(
    input: AddItemInputV1,
    options: Readonly<{
      operationId: string;
      signal?: AbortSignal;
    }>,
  ): Promise<AddItemResultV1>;
}
```

Các ID là chuỗi không rỗng trong phạm vi đã thống nhất. `quantity` là số nguyên dương, không phải delta âm để xóa sản phẩm. `revision` và `itemCount` là số nguyên không âm trong giới hạn safe integer của JavaScript; revision tăng theo thay đổi được backend xác nhận trong cùng `cartId`.

Provider chịu trách nhiệm validate input. Đặt interface ở package chung giúp kiểm tra khi build, nhưng JavaScript thuần hoặc remote cũ vẫn có thể gọi sai ở runtime. Backend tiếp tục validate và authorize; cart frontend không được tin một `cartId` chỉ vì caller gửi nó.

### Semantics thành công và lỗi

| Kết quả | Cam kết | Consumer nên làm gì |
| --- | --- | --- |
| `committed` | Backend đã xác nhận mutation; snapshot thuộc đúng cart và scope hiện tại | Bỏ trạng thái pending, dùng kết quả xác nhận hoặc đọc lại owner |
| `rejected` | Provider xác định thao tác này không được áp dụng | Hiển thị thông báo theo code; không tạo success event |
| `unknown` | Chưa xác định được thao tác đã commit hay chưa | Reconcile qua owner; nếu retry cùng ý định thì giữ `operationId` |
| Promise reject | Lỗi ngoài các kết quả đã mô hình hóa, như lỗi lập trình hoặc adapter hỏng | Report, hiển thị lỗi an toàn và không suy ra “chưa commit” |

Nếu request timeout sau khi backend đã thêm sản phẩm, trả `rejected` sẽ làm consumer hiểu sai rằng có thể tạo thao tác mới. Vì vậy, ví dụ này tách `unknown` để giữ trạng thái “chưa biết” thành một phần của contract.

`operationId` xác định một ý định logic. Dùng cùng ID khi retry cùng input; tạo ID mới khi người dùng thật sự muốn thêm lần nữa. Backend phải hỗ trợ deduplication/idempotency với scope và thời hạn cụ thể; một field tên `operationId` không tự tạo ra bảo đảm đó.

`signal` cho phép yêu cầu dừng chờ hoặc hủy request nếu adapter hỗ trợ. Nó **không cam kết rollback** một mutation đã được server xử lý. Contract cần ghi rõ cancellation trả `unknown` hay reject Promise trong implementation thật; ở ví dụ này, khi đã gửi request và không biết kết quả, provider trả `unknown`.

Consumer cũng phải viết nhánh xử lý `unknown` và `catch`. Chỉ test happy path `committed` là chưa đủ để đưa command vào production.

Event `shop.cart.updated.v1` chỉ phát sau xác nhận, không dùng để quyết định Promise command có thành công hay không. Một subscriber badge hỏng không được biến mutation đã commit thành lỗi thêm sản phẩm.

## Thiết kế event và schema

### Envelope và ý nghĩa payload

Dùng lại event trong trang [Events và message bus](/docs/giao-tiep-va-trang-thai/events), với các giá trị minh họa:

```json
{
  "type": "shop.cart.updated.v1",
  "eventId": "event-demo-001",
  "source": "cart",
  "occurredAt": "2026-03-01T08:00:00.000Z",
  "correlationId": "operation-demo-001",
  "payload": {
    "cartId": "cart-demo",
    "revision": 42,
    "itemCount": 3
  }
}
```

| Field | Semantics |
| --- | --- |
| `type` | Namespace, domain, sự việc đã xảy ra và major version |
| `eventId` | ID của một event logic; giữ nguyên khi relay hoặc phát lại |
| `source` | Owner khai báo phát event; chỉ hỗ trợ routing/debug, không xác thực danh tính |
| `occurredAt` | Thời điểm publisher tạo event; không dùng để xếp revision |
| `correlationId` | Liên kết thao tác với notification; có thể dùng `operationId` của command |
| `payload.cartId` | Phạm vi dữ liệu; chỉ so revision trong cùng cart |
| `payload.revision` | Revision của snapshot do backend xác nhận, không phải số event consumer đã nhận |
| `payload.itemCount` | Tổng quantity, không phải số dòng và không phải delta |

Contract v1 giả định bus trong memory: không replay, không ACK, không tự retry. Subscriber đến muộn query snapshot từ owner. Nếu đổi sang một transport có delivery khác, cần mô tả lại bridge và recovery policy; giữ nguyên JSON shape không đủ để giữ nguyên hành vi.

### Schema kiểm tra ở runtime

TypeScript type bị xóa khi compile. `JSON.parse(text) as CartUpdatedV1` không kiểm tra một field nào; nó chỉ khiến compiler tin lời bạn.

Với wire contract cần nhiều ngôn ngữ/tooling cùng đọc, mình ưu tiên JSON Schema và sinh type hoặc validator từ nguồn đó nếu toolchain hỗ trợ. Với ứng dụng thuần TypeScript, một schema library có type inference cũng hợp lý. Tránh duy trì schema và interface riêng mà không có test kiểm tra chúng khớp nhau.

Schema rút gọn cho event trên dùng JSON Schema Draft 2020-12:

```json title="contracts/cart-updated.v1.schema.json"
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "title": "Shop cart updated v1",
  "type": "object",
  "required": [
    "type", "eventId", "source", "occurredAt", "correlationId", "payload"
  ],
  "properties": {
    "type": { "const": "shop.cart.updated.v1" },
    "eventId": { "$ref": "#/$defs/id" },
    "source": { "const": "cart" },
    "occurredAt": { "type": "string", "format": "date-time" },
    "correlationId": { "$ref": "#/$defs/id" },
    "payload": {
      "type": "object",
      "required": ["cartId", "revision", "itemCount"],
      "properties": {
        "cartId": { "$ref": "#/$defs/id" },
        "revision": { "$ref": "#/$defs/count" },
        "itemCount": { "$ref": "#/$defs/count" }
      },
      "additionalProperties": true
    }
  },
  "additionalProperties": true,
  "$defs": {
    "id": {
      "type": "string",
      "minLength": 1,
      "maxLength": 200,
      "pattern": "\\S"
    },
    "count": {
      "type": "integer",
      "minimum": 0,
      "maximum": 9007199254740991
    }
  }
}
```

Giới hạn ID 200 ký tự là policy minh họa, cần thống nhất với API thật. Pattern yêu cầu có ít nhất một ký tự không phải whitespace; nó không tự trim hoặc chuẩn hóa ID.

`properties` mô tả field, còn `required` mới bắt buộc field phải có. `additionalProperties: true` chủ động cho phép consumer v1 đọc event có thêm field, miễn các field cũ vẫn giữ type và nghĩa.

Vậy có nên luôn cho phép unknown fields? Không. Với command chứa lựa chọn ảnh hưởng nghiệp vụ, silently bỏ qua một option mới có thể khiến thao tác được thực hiện sai ý định. Mình cho phép field bổ sung ở notification này, nhưng command cần policy riêng: reject option không hiểu hoặc kiểm tra capability trước khi gửi.

<Callout type="warn" title="Format không luôn là validation">
  Với Draft 2020-12, `format` mặc định có thể chỉ là annotation. Chọn validator hỗ trợ đúng draft và bật format assertion hoặc cấu hình kiểm tra `date-time` phù hợp. Nếu protocol bắt buộc timestamp ISO UTC chuẩn như ví dụ, bổ sung ràng buộc đó; `date-time` cũng có thể cho phép timezone offset khác UTC.
</Callout>

### Decode dữ liệu tại boundary

Boundary nhận dữ liệu bên ngoài nên bắt đầu từ `unknown`, validate rồi chuyển thành model mà consumer dùng. Ví dụ dưới đây minh họa một decoder nhỏ chỉ cho payload; envelope và timestamp cần validator riêng như schema phía trên.

```ts title="contracts/decode-cart-snapshot.ts"
import type { CartSnapshotV1 } from './cart-commands';

function isRecord(value: unknown): value is Record<string, unknown> {
  return typeof value === 'object'
    && value !== null
    && !Array.isArray(value);
}

function isId(value: unknown): value is string {
  return typeof value === 'string'
    && value.length <= 200
    && value.trim().length > 0;
}

function isCount(value: unknown): value is number {
  return typeof value === 'number'
    && Number.isSafeInteger(value)
    && value >= 0;
}

export function decodeCartSnapshotV1(value: unknown): CartSnapshotV1 {
  if (!isRecord(value)
    || !isId(value.cartId)
    || !isCount(value.revision)
    || !isCount(value.itemCount)) {
    throw new TypeError('Invalid cart snapshot v1');
  }

  // Copy các field public: không giữ reference tới object của publisher.
  return Object.freeze({
    cartId: value.cartId,
    revision: value.revision,
    itemCount: value.itemCount,
  });
}
```

Decoder chấp nhận unknown fields nhưng chỉ trả phần v1 công bố. Consumer không phụ thuộc vào field mới bằng cách đọc lén object thô. Vì các field trong snapshot đều là primitive, shallow freeze đủ cho model này; thêm object lồng nhau thì phải xét lại chính sách copy/freeze.

Decoder cũng không biến `"3"` thành `3`, không gán count sai thành `0`. Coercion và default tại boundary có thể che lỗi producer và biến “không hợp lệ” thành “giỏ rỗng”. Chỉ dùng default khi contract đã công bố rõ hành vi đó.

Với message iframe, kiểm tra `event.origin` và `event.source` trước khi decode; bên gửi dùng `targetOrigin` cụ thể. Schema validation kiểm tra shape, không kiểm tra quyền của người gửi. Với props/capabilities cùng realm, kiểm tra các cấu hình và function cần thiết khi mount, còn command input vẫn validate mỗi lần gọi.

## Quy tắc tương thích

### Hai chiều cần kiểm tra

Khi deploy độc lập, cần kiểm tra ít nhất hai tổ hợp:

1. **Consumer cũ với provider mới**: provider mới có tiếp tục nhận input cũ và cung cấp output mà consumer cũ hiểu không?
2. **Consumer mới với provider cũ**: consumer mới có fallback khi provider chưa có field hoặc capability mới không?

“Thêm field optional là an toàn” thường chỉ đúng sau khi biết field nằm ở input hay output, consumer xử lý unknown field thế nào và field có làm đổi nghĩa thao tác hay không.

| Thay đổi | Consumer cũ + provider mới | Consumer mới + provider cũ |
| --- | --- | --- |
| Thêm field output optional, giữ nghĩa field cũ | Thường tương thích nếu consumer bỏ qua field chưa biết | Tương thích nếu consumer không bắt buộc field mới và có fallback |
| Thêm input optional với default giữ hành vi cũ | Input cũ vẫn chạy được | Chỉ an toàn nếu consumer không yêu cầu hành vi mới từ provider cũ |
| Thêm input bắt buộc | Breaking: request cũ thiếu field | Không bảo đảm semantics nếu provider cũ bỏ qua field |
| Xóa hoặc đổi tên field output đã công bố | Breaking với consumer dùng field đó | Consumer mới có thể đọc provider cũ qua adapter, không tự động tương thích |
| Đổi `number` sang `string` | Breaking | Breaking nếu không có adapter rõ ràng |
| Thêm giá trị enum trong output | Có thể breaking với switch exhaustive của consumer cũ | Consumer mới có thể xử lý tập giá trị cũ, nhưng vẫn phải test |
| Thêm giá trị được nhận trong input | Provider mới vẫn nhận giá trị cũ | Provider cũ có thể reject giá trị mới |
| Đổi nghĩa field dù giữ type | Breaking về semantics | Hai bên hiểu khác nhau, không sửa được bằng cast |
| Siết giới hạn quantity hoặc ID | Có thể từ chối input từng hợp lệ | Cần kiểm tra producer cũ và policy lỗi mới |

Trong hệ thống cần rollout thứ tự bất kỳ, hai chiều đều phải đạt yêu cầu. Nếu chỉ hỗ trợ consumer cũ với provider mới, bạn vẫn có thể deploy độc lập theo thứ tự provider trước; hãy ghi điều kiện đó thay vì hứa “deploy lúc nào cũng được”.

### Các thay đổi tưởng nhỏ nhưng có thể breaking

Thêm `status: 'partially-committed'` vào result của `addItem` không đơn giản là mở rộng union. Consumer cũ có thể chỉ biết `committed`, `rejected` và `unknown`; nhánh mới khiến UI không biết giỏ đã thay đổi đến đâu. Với result v1 đang là tập trạng thái đóng, mình chọn version mới hoặc capability mới.

Ngược lại, nếu ngay từ đầu contract định nghĩa mã lỗi là tập mở và consumer có fallback “Không thực hiện được thao tác”, thêm một mã có thể không breaking. Tính tương thích nằm trong cam kết đã công bố, không nằm ở nhận xét “chỉ thêm một string”.

`optional`, `null` và thiếu field cũng không giống nhau. Ví dụ `couponCode?: string` có thể nghĩa là “không yêu cầu đổi coupon”; `couponCode: null` có thể nghĩa là “xóa coupon”. Nếu provider tự coi cả hai là chuỗi rỗng, consumer và provider đã mất một phần ý nghĩa thao tác.

Thay đổi hành vi đồng bộ thành bất đồng bộ, publish event trước commit, đổi từ snapshot sang delta, hoặc reset draft khi update theme đều có thể breaking dù interface giữ nguyên. Test contract phải quan sát hành vi, không chỉ so schema.

<Callout type="warn" title="Không dùng tolerance để đoán nghiệp vụ">
  Bỏ qua field mới trong một notification có thể hợp lý. Bỏ qua `reservationRequired: true` trong một command đặt hàng thì không. Với option làm thay đổi kết quả nghiệp vụ, negotiate capability hoặc reject rõ ràng; đừng đoán ý định của caller.
</Callout>

## Versioning và capability negotiation

### Phân biệt các loại version

| Version | Ví dụ minh họa | Dùng để làm gì |
| --- | --- | --- |
| Contract package | `@shop/contracts@1.4.0` | Quản lý artifact chứa types, schemas và tài liệu theo SemVer |
| Protocol major | `shop.cart.updated.v1` | Nhận diện wire contract mà runtime phải xử lý |
| Remote build | `cart-build-abc123` | Debug, rollout và rollback implementation |

Một build mới có thể giữ nguyên protocol v1. Package `1.4.0` có thể bổ sung schema/capability không breaking mà không đổi mọi event thành `.v1.4`. SemVer yêu cầu public API rõ: major cho breaking change, minor cho chức năng tương thích và patch cho sửa lỗi tương thích.

Nhưng chỉ bump major của package là chưa đủ. Consumer đã bundle type v1 vẫn có thể tải provider v2 qua remote URL; lockfile của consumer không điều khiển artifact remote tại runtime. Cần version trong protocol, manifest hoặc export tương ứng để tránh ghép sai.

Mình đặt major trong tên event, còn các capability dùng định danh rõ như `shop.cart.add-item.v1`. Không cần một “global version” buộc locale, navigation và cart cùng nâng cấp chỉ vì một domain thay đổi.

### Kiểm tra capability trước khi mount

Shell có thể đọc một descriptor ổn định trước khi inject capabilities. Ví dụ dưới đây minh họa quy ước descriptor; loader thật phải kiểm tra cấu trúc descriptor ở runtime và xác minh provider export tương ứng.

```json title="Ví dụ descriptor của catalog remote"
{
  "descriptorVersion": 1,
  "name": "catalog",
  "buildId": "catalog-build-example",
  "mountContract": "shop.catalog.mount.v1",
  "requires": ["shop.cart.add-item.v1"],
  "optional": ["shop.cart.apply-coupon.v1"]
}
```

Nếu provider có `add-item.v1` nhưng chưa có `apply-coupon.v1`, catalog mount bình thường và ẩn tính năng coupon. Nếu thiếu capability bắt buộc hoặc không hiểu mount contract, shell không gọi `mount`; nó chọn build đã biết tương thích hoặc hiển thị fallback có telemetry.

Capability phải mô tả một hành vi đủ cụ thể. Cờ `supportsCart: true` không nói cart có nhận quantity, hỗ trợ idempotency hay trả snapshot gì. Descriptor cũng không phải bằng chứng bảo mật: implementation có thể khai báo sai, nên vẫn cần contract tests.

Protocol descriptor/handshake cần ổn định, có timeout và quy tắc từ chối version không hiểu. Với iframe, chỉ mark remote ready sau handshake đã validate; với module cùng realm, kiểm tra export/capability trước mount. Negotiation không thay cho một adapter hoặc implementation thật của capability đó.

## Migration không bắt buộc deploy đồng thời

### Expand và chuyển consumer

Giả sử shell muốn hiển thị cả số dòng và tổng quantity. Không đổi nghĩa `itemCount` trong v1. Ví dụ v2 có thể công bố:

```json title="Payload v2 minh họa"
{
  "cartId": "cart-demo",
  "revision": 42,
  "unitCount": 3,
  "lineCount": 2
}
```

`unitCount` là tổng quantity, `lineCount` là số dòng trong giỏ theo quy tắc gộp dòng của backend. Hai dòng có thể khác variant hoặc cấu hình dù cùng sản phẩm; hãy định nghĩa “dòng” theo domain thật. Provider cần API có đủ dữ liệu, không suy `lineCount` từ `itemCount`.

Với thay đổi này, một trình tự rollout có thể là:

1. **Công bố v2** cùng semantics, fixtures, validator và bảng consumer bị ảnh hưởng; giữ v1 nguyên nghĩa.
2. **Mở rộng provider** để hỗ trợ v1 và v2. Khi cart commit snapshot có đủ dữ liệu, provider tạo projection đúng cho từng version.
3. **Nâng consumer dần**: shell mới ưu tiên v2 nếu provider có capability tương ứng, vẫn chạy v1 khi rollback về provider cũ. Với v1, badge tổng quantity vẫn chạy; thông tin số dòng bị ẩn thay vì đoán.
4. **Đo adoption và lỗi** theo contract major/build, test người dùng có phiên browser cũ và consumer đã cache bundle.
5. **Ngừng v1** chỉ sau khi consumer còn được hỗ trợ không cần nó và cửa sổ rollback đã kết thúc.

Nếu chỉ cần thêm `lineCount` optional vào output hiện có, giữ v1 cũng có thể phù hợp khi consumer cũ cho phép unknown fields và consumer mới có fallback. Ví dụ trên dùng v2 để minh họa migration khi thay đổi public naming/shape; không phải cứ thêm một field là phải nâng major.

Khi provider phát cả event v1 và v2 cho cùng một thay đổi, một consumer nên chọn một version làm đường cập nhật chính. Nếu bridge relay và consumer nghe cả hai, cần dedupe theo operation/revision và cart scope; đừng coi chúng là hai mutation rồi cộng badge hai lần. Việc map identity giữa các representation cũng phải được ghi trong migration contract.

### Rollback và gỡ contract cũ

Rollback provider là bài kiểm tra consumer mới với provider cũ trong thực tế. Nếu shell mới bắt buộc v2 mà cart rollback chỉ có v1, hai build dù đều “đã qua CI” vẫn không chạy cùng nhau.

Giữ fallback trong consumer hoặc giới hạn rollback vào các build còn hỗ trợ capability cần thiết. Khi không có tổ hợp tương thích, fallback có kiểm soát tốt hơn một màn hình trông bình thường nhưng dùng semantics sai.

Không gỡ v1 chỉ vì mọi deployment trên dashboard đã là bản mới. Tab đang mở có thể còn bundle cũ; CDN, service worker hoặc cơ chế rollback có thể phục vụ artifact cũ. Cửa sổ hỗ trợ phải dựa vào chính sách cache, tuổi thọ phiên và cách buộc reload an toàn của ứng dụng, không có một số ngày chung cho mọi hệ thống.

Telemetry là dữ liệu hỗ trợ quyết định, không chứng minh tuyệt đối rằng không còn consumer cũ. Kết hợp quan sát với danh sách consumer, lịch deprecation và policy hỗ trợ đã thống nhất.

## Phân phối và kiểm thử contract

### Package chung nhưng không chung implementation

Một package contract có thể chứa:

- Public types và định danh event/capability.
- Schemas hoặc runtime validators nhỏ, không phụ thuộc framework UI.
- Fixtures hợp lệ/không hợp lệ cùng test helpers.
- Tài liệu semantics, changelog và policy deprecation.

Không đưa Redux store, React Context, query client hoặc service đang giữ session vào package đó. Types được import bằng `import type` không tạo runtime singleton; validator có thể bundle nhiều bản mà không sao, nhưng bus/controller có state thì không nên trông chờ package chung để bảo đảm một instance.

Consumer chỉ nâng dependency khi cần, provider vẫn phải giữ public protocol đã hứa hỗ trợ. Nếu mỗi lần package thay đổi đều buộc tất cả remote rebuild cùng nhau, bạn đã có một release train chung chứ chưa có deploy độc lập.

Trong monorepo, chạy test provider–consumer cùng workspace giúp phát hiện lỗi sớm nhưng dễ bỏ sót phiên bản đã deploy. Cần giữ fixtures và test cho consumer cũ còn được hỗ trợ, không chỉ test mọi package ở HEAD.

### Ma trận kiểm thử và fixture

Tối thiểu hãy kiểm tra các tổ hợp được policy của bạn cho phép:

| Consumer | Provider | Mục tiêu |
| --- | --- | --- |
| Cũ còn hỗ trợ | Mới | Input cũ vẫn chạy, output mới vẫn đọc được |
| Mới | Cũ trong cửa sổ rollback | Fallback/capability negotiation hoạt động |
| Mới | Mới | Tính năng mới đúng semantics |
| Version không hỗ trợ | Bất kỳ | Từ chối có kiểm soát, không mount hoặc mutate nhầm |

Một test nhỏ cho decoder phía trên có thể chạy bằng Node với TypeScript đã compile, hoặc test runner có hỗ trợ TypeScript:

```ts title="contracts/decode-cart-snapshot.test.ts"
import assert from 'node:assert/strict';
import { decodeCartSnapshotV1 } from './decode-cart-snapshot';

const oldFixture = {
  cartId: 'cart-demo',
  revision: 42,
  itemCount: 3,
};

assert.deepEqual(decodeCartSnapshotV1(oldFixture), oldFixture);

// Output mới bổ sung field không phá consumer chỉ cần projection v1.
assert.deepEqual(
  decodeCartSnapshotV1({ ...oldFixture, lineCount: 2 }),
  oldFixture,
);

for (const invalid of [
  { ...oldFixture, itemCount: '3' },
  { ...oldFixture, itemCount: -1 },
  { ...oldFixture, revision: Number.MAX_SAFE_INTEGER + 1 },
  { ...oldFixture, cartId: '   ' },
  { cartId: 'cart-demo', revision: 42 },
  null,
  [],
]) {
  assert.throws(() => decodeCartSnapshotV1(invalid), TypeError);
}

const raw = { ...oldFixture };
const decoded = decodeCartSnapshotV1(raw);
raw.itemCount = 99;
assert.equal(decoded.itemCount, 3);
assert.equal(Object.isFrozen(decoded), true);
```

Test này kiểm tra payload shape và projection, chưa chứng minh event envelope, command hay lifecycle đúng. Với schema đầy đủ, thêm test event sai `type`, thiếu `correlationId`, timestamp sai và các field bổ sung; dùng cấu hình validator giống production.

Với semantics, tạo scenario có hai dòng quantity lần lượt là 2 và 1, rồi assert badge nhận 3 chứ không phải 2. Fixture chứa `itemCount: 3` tự nó không phát hiện provider tính sai con số.

Với behavior, test mount/update/unmount, timeout không rõ commit, retry cùng operation, subscriber mount muộn và rollback build. Consumer-driven contract tests giúp ghi nhận kỳ vọng thật của từng consumer; provider phải chạy chúng với implementation thật hoặc adapter sát thực tế, không chỉ mock cũng trả đúng fixture đó.

## Failure modes và quan sát

| Triệu chứng | Nguyên nhân có thể | Hành động |
| --- | --- | --- |
| Build thành công nhưng badge sai | Đổi semantics count, dùng sai cart scope hoặc snapshot cũ | Kiểm tra owner, đơn vị, cart ID và revision; thêm test nghiệp vụ |
| Chỉ lỗi sau deploy hoặc rollback | Ghép consumer/provider ngoài ma trận hỗ trợ | Ghi contract major và build IDs; kiểm tra negotiation |
| Consumer cũ reject event mới | Validator cũ cấm unknown fields | Xác nhận policy v1, sửa compatibility hoặc phát version mới |
| Bấm thêm hai lần sau timeout gây duplicate | Consumer coi timeout là reject, tạo operation mới | Mô hình hóa unknown và kiểm tra idempotency backend |
| Mount thành công nhưng listener nhân đôi | Lifecycle cleanup chưa được test | Test unmount lặp, remount và response muộn |
| Event có `source: 'cart'` nhưng từ nơi không tin cậy | Tin field trong payload như danh tính | Kiểm tra transport origin/source và authorization backend |

Ở boundary, ghi metadata đủ để tái hiện tổ hợp: remote name/build, contract ID, capability đã chọn, loại lỗi validation, `eventId` hoặc `correlationId` khi phù hợp. Không log nguyên payload theo mặc định; event có thể chứa dữ liệu cá nhân khi contract mở rộng.

Policy khi lỗi phải phân biệt boundary. Mount thiếu capability bắt buộc thì không mount. Event không hợp lệ thì drop/report và revalidate snapshot nếu cần, không fallback count về `0`. Command input không hợp lệ thì từ chối trước mutation; command đã gửi mà chưa biết kết quả thì reconcile, không tự động phát một command mới.

## Checklist trước khi công bố contract

- [ ] Có owner và danh sách consumer, không expose store hoặc model nội bộ không cần thiết.
- [ ] Input/output ghi rõ required, optional, null, đơn vị, scope và nguồn chuẩn.
- [ ] Command phân biệt committed, rejected và chưa biết kết quả; policy retry/cancellation được công bố.
- [ ] Event ghi rõ snapshot hay delta, delivery, replay và cách lấy state hiện tại.
- [ ] Props có quy tắc update; mount/unmount, cleanup và response muộn đã được test.
- [ ] Dữ liệu ngoài được validate từ `unknown`; policy unknown fields và format được cấu hình rõ.
- [ ] Security không dựa vào field `source`, UI permission hoặc TypeScript type.
- [ ] Contract version được phân biệt với package version và remote build.
- [ ] Test cả consumer cũ/provider mới và consumer mới/provider cũ trong phạm vi hỗ trợ.
- [ ] Có capability negotiation hoặc routing version rõ, cùng fallback khi không tương thích.
- [ ] Có kế hoạch expand/migrate/remove, telemetry adoption và cửa sổ rollback.
- [ ] Fixtures và behavior tests bảo vệ semantics, không chỉ schema.

Bước thực hành: chọn một boundary đang khiến hai remote phải deploy cùng nhau, ghi lại input, output và hành vi mà consumer thật sự cần. Sau đó thử thay implementation provider hoặc chạy consumer với build provider cũ. Những chỗ phải đoán hay sửa đồng thời chính là phần contract cần làm rõ trước tiên.
