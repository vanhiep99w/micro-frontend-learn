Header và Cart cùng cần số lượng giỏ hàng. Nếu mỗi app gọi API riêng thì có thể tải trùng. Nếu chỉ dùng cache mà không làm mới sau khi thêm hàng, hai nơi có thể tiếp tục hiện số cũ. **Cùng một endpoint không có nghĩa là cùng một cache.**

Bài này nối tiếp [State ownership](/docs/giao-tiep-va-trang-thai/state-ownership): owner không chỉ giữ state trong memory mà còn tải dữ liệu từ backend. Đây là nhánh **backend/cache dùng chung** trong [bản đồ giao tiếp](/docs/giao-tiep-va-trang-thai#các-cách-giao-tiếp-và-bài-đọc-tiếp), có thể kết hợp API qua `mount` và event.

<Callout type="info" title="Bắt đầu bằng cache nhỏ, chưa cần học thư viện">
  Ví dụ đầu dùng JavaScript và API giả trong memory để nhìn rõ thứ tự gọi. Phần sau có mẫu TanStack Query v5 đầy đủ hơn. Không có endpoint shop thật được triển khai bởi site docs; số lần đọc trong bài tập không phải số request HTTP.
</Callout>

## Ba việc khác nhau khi lấy dữ liệu

| Việc | Ai làm trong thiết kế này? |
| --- | --- |
| Xác nhận dữ liệu nghiệp vụ | Backend Cart |
| Gọi API, lưu cache, quyết định làm mới | Module data do team Cart cung cấp |
| Hiển thị loading, số lượng hoặc lỗi | Header và Cart UI |

Header không cần biết endpoint, key cache hay thư viện của Cart. Nó nhận một API như `getSummary()` qua tham số mount. Backend vẫn kiểm tra quyền và nghiệp vụ; cache frontend chỉ giữ bản dữ liệu để hiển thị.

Nếu hai app độc lập cùng tải backend, chúng vẫn phối hợp gián tiếp qua dữ liệu server, nhưng không tự biết app kia vừa sửa gì. Cần chọn lúc tải lại, event báo dữ liệu cũ hoặc server push. Dùng chung một data API là lựa chọn khi cần tránh lặp việc và kiểm soát một đường cập nhật.

## Module data chia sẻ kết quả và lần tải đang chạy

Mẫu tối thiểu dưới đây giữ một summary và một Promise đang tải. Promise là kết quả sẽ hoàn tất về sau; hai app có thể chờ cùng Promise thay vì gọi API hai lần.

```js title="basic/cart-data.js" sourceFile="basic/cart-data.js" sourceRegion="main"
export function createCartData(api) {
  let cached;
  let pending;
  let generation = 0;

  function invalidate() {
    generation += 1;
    cached = undefined;
    pending = undefined;
  }

  function getSummary() {
    if (cached !== undefined) return Promise.resolve(cached);
    if (pending) return pending;

    const started = generation;
    const request = Promise.resolve().then(() => api.getSummary())
      .then((summary) => {
        if (started === generation) cached = Object.freeze({ ...summary });
        return Object.freeze({ ...summary });
      })
      .finally(() => {
        if (pending === request) pending = undefined;
      });
    pending = request;
    return request;
  }

  return {
    getSummary,
    invalidate,
    async addItem() {
      await api.addItem();
      invalidate();
    },
  };
}
```

Đọc `getSummary()` từ trên xuống:

1. Có `cached` thì dùng lại, không gọi API.
2. Chưa có dữ liệu nhưng có `pending` thì chờ cùng lần tải đang chạy.
3. Chưa có cả hai thì bắt đầu một lần đọc API, giữ Promise trong `pending`.
4. Khi xong, lưu kết quả và dọn `pending`. Nếu lỗi, không giữ lỗi như dữ liệu thành công; lần gọi sau có thể tải lại.

`invalidate()` nghĩa là **đánh dấu dữ liệu hiện có không còn dùng lại được**. Nó tăng `generation`, một số thứ tự cục bộ, để response của lần tải trước invalidation không được ghi lại vào cache mới. Nó không hủy request ở backend.

`addItem()` chờ API thay đổi dữ liệu rồi invalidate. Nó chưa cập nhật UI nào; bên nối cần gọi refresh hoặc data owner cần công bố subscription. Như vậy ta thấy rõ thay đổi backend và làm mới UI là hai bước riêng.

## Hai UI nhận cùng data API từ shell

### Code một UI đọc dữ liệu

Cùng một hàm mount dùng cho hai vùng Header và Cart trong bài tập. Trong ứng dụng thật, hai remote có UI khác nhau nhưng cùng cách gọi data API:

```js title="basic/summary.js" sourceFile="basic/summary.js" sourceRegion="main"
export function mount({ container, data, name }) {
  const label = document.createElement('p');
  container.append(label);
  let active = true;
  let requestId = 0;

  async function refresh() {
    const current = ++requestId;
    label.textContent = `${name}: đang tải`;
    try {
      const summary = await data.getSummary();
      if (active && current === requestId) {
        label.textContent = `${name}: ${summary.itemCount} món`;
      }
    } catch {
      if (active && current === requestId) label.textContent = `${name}: lỗi tải`;
    }
  }

  void refresh();
  return {
    refresh,
    unmount() { active = false; label.remove(); },
  };
}
```

`requestId` giúp UI không áp dụng kết quả của lần refresh cũ khi lần mới đã bắt đầu. `active` chặn cập nhật sau unmount. Generation trong data module bảo vệ **cache**; request ID/active ở đây bảo vệ **instance UI**. Hai lớp giải quyết hai vị trí ghi khác nhau.

```js title="basic/shell.js" sourceFile="basic/shell.js" sourceRegion="main"
import { createFakeApi } from './fake-api.js';
import { createCartData } from './cart-data.js';
import { mount } from './summary.js';

let reads = 0;
const api = createFakeApi(() => {
  document.querySelector('#reads').textContent = `Số lần đọc API giả: ${++reads}`;
});
const data = createCartData(api);
const header = mount({ container: document.querySelector('#header'), data, name: 'Header' });
const cart = mount({ container: document.querySelector('#cart'), data, name: 'Cart' });

const add = document.querySelector('#add');
const notice = document.querySelector('#notice');
add.addEventListener('click', async () => {
  add.disabled = true;
  try {
    await data.addItem();
    notice.textContent = 'Đã thêm; đang làm mới hai UI';
    await Promise.all([header.refresh(), cart.refresh()]);
  } catch {
    notice.textContent = 'Chưa xác nhận kết quả thêm hàng; không tự gửi lại';
  } finally {
    add.disabled = false;
  }
});
```

Lần đầu, Header và Cart gọi `getSummary` gần nhau nên chờ cùng lần tải. Khi bấm thêm hàng, API giả tăng số lượng, module xóa cache rồi hai UI gọi refresh. Lần tải mới cũng chỉ chạy một lần.

Nếu thay `createFakeApi` bằng HTTP adapter, adapter phải kiểm tra status, parse/validate JSON và truyền credential đúng cơ chế ứng dụng. `fetch` không tự reject chỉ vì HTTP 404/500. Không đưa access token vào URL hay query key.

## Khi nào dùng cache riêng và khi nào dùng chung

| Cách | Được gì? | Cần thống nhất gì? |
| --- | --- | --- |
| Mỗi domain giữ cache riêng | Ít phụ thuộc thư viện và model của app khác | Cách báo thay đổi và lúc refetch |
| Nhiều UI dùng một data API | Giấu implementation, phù hợp khác framework | API đọc/ghi, snapshot/lỗi, lifecycle instance |
| Dùng cùng QueryClient | Tận dụng query sharing của thư viện | Cùng instance, key, response shape, options và runtime tương thích |

Mình mặc định giữ cache sản phẩm trong Catalog, cache giỏ trong Cart. Chỉ chia sẻ phần cần phối hợp. Hai app cùng `new QueryClient()` vẫn có hai cache; share dependency không tự share state. Hai React root cũng không tự nhận Context của nhau, cần cấp client rõ ràng nếu chọn mô hình đó.

Thử khác biệt bằng app dùng TanStack Query Core thật:

Ở bản **Cùng QueryClient**, hai observer — hai nơi đang theo dõi query — chờ một lần tải dữ liệu. Đổi sang **Hai QueryClient riêng**, chúng có hai lần đọc. Bấm **Trả response đang chờ** để hoàn tất. API là Promise trong memory có nút điều khiển, không phải request HTTP. Demo còn có thao tác mutation khi GET đang chờ để quan sát cách chặn response cũ.

## Làm mới dữ liệu sau thay đổi

Nếu các UI dùng chung cache, owner invalidate đúng dữ liệu của domain sau mutation. Với cache riêng, app sửa dữ liệu phát event như “giỏ đã đổi”; mỗi app nhận tự làm mới cache của mình. Không gửi tên query key hay lệnh `invalidateQueries` nội bộ của một app sang app khác.

Nếu mutation đã thành công nhưng GET refresh bị lỗi, UI cần báo dữ liệu chưa cập nhật được, **không tự gửi lại mutation**. Timeout khi gửi mutation còn là kết quả chưa biết; retry phải theo contract chống trùng backend, không chỉ theo nút disabled.

| Tình huống | Hành vi cần có |
| --- | --- |
| App mount sau event | Đọc snapshot/tải dữ liệu, không chỉ chờ event mới |
| Remote unmount nhưng header còn dùng cache | Chỉ gỡ observer remote, không clear toàn bộ client |
| User/tenant đổi | Khóa scope cũ, hủy/bỏ kết quả cũ và xóa cache riêng tư |
| Response GET cũ về sau mutation | Không ghi đè snapshot mới theo policy generation/revision/cancellation |
| Lỗi mạng/5xx | Retry hữu hạn cho query theo policy; không retry mọi mutation một cách mù quáng |

## Mẫu TanStack Query để tra cứu

Đây là **bộ mẫu nâng cao độc lập với cache JavaScript ở trên**, không phải code cần copy thêm vào nó. Các import ứng dụng/endpoint là giả định. Đọc theo thứ tự: `data-contract.ts` định nghĩa key/scope và parser → `summary-query.ts` gọi GET → `cart-runtime.tsx` cấp client cho UI → `use-add-item.ts` gửi thay đổi và invalidate.

**Query key** là địa chỉ dữ liệu trong cache. Summary, detail hoặc dữ liệu của user khác không được vô tình chung địa chỉ. Scope gồm user/guest, tenant, cart và generation của phiên; không chứa credential. Tên `v1` trong key là version cache contract, không tự là version REST API.

<details>
<summary>cart/data-contract.ts</summary>

```ts title="cart/data-contract.ts" sourceFile="cart/data-contract.ts" sourceRegion="main"
export type CartScope = Readonly<{
  tenantId: string;
  subjectKey: string; // User/guest tag, không phải credential.
  sessionEpoch: number; // Generation cục bộ, tăng khi scope auth thay đổi.
  cartId: string;
}>;

export type CartSummary = Readonly<{
  cartId: string;
  itemCount: number; // Tổng quantity, không phải số dòng.
  revision: number;
}>;

export const cartKeys = {
  root: (scope: CartScope) => ['cart', 'v1', scope] as const,
  summary: (scope: CartScope) =>
    [...cartKeys.root(scope), 'summary'] as const,
  detail: (scope: CartScope) =>
    [...cartKeys.root(scope), 'detail'] as const,
};

export function parseSummary(
  value: unknown,
  expectedCartId: string,
): CartSummary {
  if (typeof value !== 'object' || value === null) {
    throw new Error('Invalid cart summary');
  }

  const data = value as Record<string, unknown>;
  if (
    data.cartId !== expectedCartId ||
    typeof data.itemCount !== 'number' ||
    !Number.isSafeInteger(data.itemCount) || data.itemCount < 0 ||
    typeof data.revision !== 'number' ||
    !Number.isSafeInteger(data.revision) || data.revision < 0
  ) {
    throw new Error('Invalid cart summary');
  }

  return {
    cartId: expectedCartId,
    itemCount: data.itemCount,
    revision: data.revision,
  };
}
```

```ts title="cart/summary-query.ts" sourceFile="cart/summary-query.ts" sourceRegion="main"
import { queryOptions } from '@tanstack/react-query';
import { cartKeys, parseSummary, type CartScope } from './data-contract';

export class ApiError extends Error {
  constructor(public readonly status: number) {
    super(`Cart API failed: ${status}`);
  }
}

export function cartBaseUrl(scope: CartScope): string {
  const tenant = encodeURIComponent(scope.tenantId);
  const cart = encodeURIComponent(scope.cartId);
  return `/api/tenants/${tenant}/carts/${cart}`;
}

export function cartSummaryOptions(scope: CartScope) {
  return queryOptions({
    queryKey: cartKeys.summary(scope),
    queryFn: async ({ signal }) => {
      const response = await fetch(`${cartBaseUrl(scope)}/summary`, {
        credentials: 'same-origin',
        signal,
      });
      if (!response.ok) throw new ApiError(response.status);
      const body: unknown = await response.json();
      return parseSummary(body, scope.cartId);
    },
    staleTime: 15_000,
    gcTime: 5 * 60_000,
    retry: (failureCount, error) =>
      error instanceof ApiError &&
      [502, 503, 504].includes(error.status) && failureCount < 2,
  });
}
```

```tsx title="cart/use-add-item.ts" sourceFile="cart/use-add-item.ts" sourceRegion="main"
import { useMutation, type QueryClient } from '@tanstack/react-query';
import { cartKeys, type CartScope } from './data-contract';
import { ApiError, cartBaseUrl } from './summary-query';

type AddItemInput = Readonly<{
  sku: string;
  quantity: number;
  idempotencyKey: string;
}>;

export function useAddItem(
  queryClient: QueryClient,
  scope: CartScope,
  isCurrentScope: (candidate: CartScope) => boolean,
) {
  return useMutation({
    mutationFn: async (input: AddItemInput) => {
      if (!isCurrentScope(scope)) throw new Error('Scope has changed');
      if (
        !input.sku.trim() ||
        !Number.isSafeInteger(input.quantity) || input.quantity <= 0 ||
        !input.idempotencyKey
      ) {
        throw new Error('Invalid add-item input');
      }

      const response = await fetch(`${cartBaseUrl(scope)}/items`, {
        method: 'POST',
        credentials: 'same-origin',
        headers: {
          'Content-Type': 'application/json',
          'Idempotency-Key': input.idempotencyKey,
        },
        body: JSON.stringify({ sku: input.sku, quantity: input.quantity }),
      });
      if (!response.ok) throw new ApiError(response.status);
    },
    retry: false,
    onSuccess: async () => {
      if (!isCurrentScope(scope)) return;
      await queryClient.invalidateQueries({
        queryKey: cartKeys.root(scope),
      });
    },
  }, queryClient);
}
```

`staleTime` là thời gian coi dữ liệu đủ mới, không phải timer tự gửi request khi hết hạn. `gcTime` giữ query inactive trước khi dọn. Invalidation thường đánh dấu stale rồi refetch query active theo options; disabled query và các options đặc biệt cần kiểm tra theo phiên bản đang pin. Các thời gian/retry trong mẫu là policy minh họa.

Tham số client thứ hai của `useQuery` cấp cùng client rõ ràng cho các UI. Runtime gọi `mount/unmount` cho client nếu không dùng Provider; chỉ owner được `dispose`, không để remote gọi `clear()` mỗi lần rời route.

## Cache nào đang làm dữ liệu cũ

| Lớp | Khi làm mới cache frontend có tự xóa lớp này không? |
| --- | --- |
| Query cache trong một client | Chỉ các query/client được tác động |
| HTTP cache browser | Không; phụ thuộc Cache-Control/validation |
| CDN/shared proxy | Không; policy phía server/edge |
| Storage/service worker | Không; cần lifecycle/version/scope riêng |

`no-store` của HTTP không tự xóa object trong QueryClient; `invalidateQueries` cũng không purge CDN. Nếu refetch vẫn trả dữ liệu cũ, kiểm tra headers, server revision và khả năng backend đọc từ replica cập nhật trễ, không chỉ nhìn số lần render.

Với SSR, tạo cache dữ liệu user theo request, không giữ mutable singleton dùng chung mọi user. Payload hydrate phải đúng scope và không chứa token. Cache riêng tư/HTML không được đẩy vào shared CDN theo policy public.

## Kiểm tra trước khi ghép thêm remote

- Hai UI cùng instance/key có chia sẻ lần tải khi đang pending không?
- Query lỗi rồi gọi lại có hoạt động, hay giữ mãi Promise đã reject?
- Mutation xong chỉ làm mới domain liên quan, không refetch toàn app?
- GET cũ, callback sau unmount và cache user cũ có bị chặn đúng chỗ không?
- Đổi client riêng/chung có thay đổi request count đúng kỳ vọng không?
