Ở bài [events](/docs/giao-tiep-va-trang-thai/events), app đăng ký muộn không biết lựa chọn đã xảy ra trước đó. Muốn giải quyết, cần có nơi **giữ dữ liệu hiện tại** để app mới mở đọc được, thay vì chỉ chờ thông báo mới.

Bài này đi theo nhánh **module/state dùng chung** của [bản đồ giao tiếp](/docs/giao-tiep-va-trang-thai#các-cách-giao-tiếp-và-bài-đọc-tiếp). Ví dụ dùng theme vì không cần backend: shell và một remote cùng đọc một lựa chọn sáng/tối, nhưng không import store nội bộ của nhau.

<Callout type="info" title="Ownership là trách nhiệm, không phải thư viện">
  Owner là module chịu trách nhiệm cập nhật một phần dữ liệu và công bố API cho bên khác dùng. Shell có thể tạo instance của module đó mà không phải tự viết mọi nghiệp vụ bên trong. Ví dụ dùng JavaScript thuần trong cùng document, không yêu cầu Redux, Pinia hay React Context.
</Callout>

## State riêng thì cứ để riêng

Nội dung đang gõ trong form Catalog không cần xuất hiện ở Cart. Đưa nó lên global store chỉ làm Cart có cơ hội phụ thuộc vào phần không liên quan.

| Dữ liệu | Nơi nên bắt đầu giữ |
| --- | --- |
| Input chưa submit, modal trong Catalog | Bên trong Catalog |
| Tab tạm thời trong Cart | Bên trong Cart UI |
| Bộ lọc cần mở lại từ link | URL, theo contract của Catalog |
| Theme dùng toàn trang | Module cấu hình chung |
| Giỏ đã được server xác nhận | Backend là nguồn chuẩn; module Cart giữ dữ liệu frontend |

**Có nhiều nơi đọc không có nghĩa mọi nơi phải tự ghi một bản.** Shell và remote có thể giữ dữ liệu để render, nhưng phải lấy từ một đường cập nhật đã thống nhất.

## Một module giữ theme cho cả shell và remote

Module dưới giữ đúng một snapshot. Snapshot là **bản dữ liệu hiện tại để đọc**, không phải lịch sử các lần thay đổi.

```js title="basic/theme.js" sourceFile="basic/theme.js" sourceRegion="main"
export function createTheme() {
  let snapshot = Object.freeze({ theme: 'light' });
  const listeners = new Set();

  return {
    getSnapshot() {
      return snapshot;
    },
    setTheme(theme) {
      if (!['light', 'dark'].includes(theme)) {
        throw new Error('Theme không được hỗ trợ');
      }
      if (snapshot.theme === theme) return;
      snapshot = Object.freeze({ theme });
      for (const notify of [...listeners]) notify();
    },
    subscribe(notify) {
      listeners.add(notify);
      return () => listeners.delete(notify);
    },
  };
}
```

Ba hàm có ba vai trò:

- `getSnapshot()` trả theme hiện tại, kể cả app vừa mount.
- `setTheme(...)` là đường yêu cầu thay đổi. Module kiểm tra giá trị, tạo snapshot mới rồi thông báo.
- `subscribe(...)` đăng ký nghe; hàm trả về dùng để ngừng nghe.

`Object.freeze` ở đây đủ cho object chỉ có một string. Consumer không được sửa `snapshot.theme` để thay đổi state; phải gọi `setTheme`. Snapshot giữ nguyên reference nếu dữ liệu không đổi, thuận tiện khi nối với các adapter như React `useSyncExternalStore`.

Không có event bus riêng trong mẫu này. Danh sách listener bên trong module đã đủ cho nhu cầu theo dõi một state nhỏ. Nó chưa cô lập lỗi listener; handler demo chỉ cập nhật text đồng bộ. Với app thật, bổ sung chính sách lỗi và lifecycle theo dữ liệu.

## Remote đọc trước hay nghe trước

Remote Settings dùng module đã nhận từ shell, không tự gọi `createTheme()`:

```js title="basic/settings.js" sourceFile="basic/settings.js" sourceRegion="main"
export function mount({ container, theme }) {
  const button = document.createElement('button');
  let active = true;

  function render() {
    button.textContent = `Remote đang dùng theme: ${theme.getSnapshot().theme}`;
  }
  function toggle() {
    const current = theme.getSnapshot().theme;
    theme.setTheme(current === 'light' ? 'dark' : 'light');
  }

  const unsubscribe = theme.subscribe(render);
  render();
  button.addEventListener('click', toggle);
  container.append(button);

  return {
    unmount() {
      if (!active) return;
      active = false;
      unsubscribe();
      button.removeEventListener('click', toggle);
      button.remove();
    },
  };
}
```

Nhìn ba dòng liên tiếp: `subscribe(render)` → `render()` → gắn UI. Đăng ký trước rồi đọc snapshot giúp app vừa mở biết **theme hiện tại**, sau đó nhận thay đổi tiếp theo. Đây là cách nối cho snapshot đồng bộ trong bộ nhớ; query bất đồng bộ còn cần xử lý response về muộn.

Remote chỉ đổi giao diện của nó. Shell cũng cần một listener riêng để đổi phần do shell quản lý. Không để remote tìm DOM của shell rồi sửa hộ.

## Shell tạo một instance và giữ lâu hơn UI

```js title="basic/shell.js" sourceFile="basic/shell.js" sourceRegion="main"
import { createTheme } from './theme.js';
import { mount } from './settings.js';

const theme = createTheme();
const label = document.querySelector('#shell-theme');
const render = () => {
  label.textContent = `Shell đang dùng theme: ${theme.getSnapshot().theme}`;
};
theme.subscribe(render);
render();

let settings;
document.querySelector('#open').addEventListener('click', () => {
  settings ??= mount({ container: document.querySelector('#settings'), theme });
});
document.querySelector('#close').addEventListener('click', () => {
  settings?.unmount();
  settings = undefined;
});
document.querySelector('#dark').addEventListener('click', () => {
  theme.setTheme('dark');
});
```

Shell tạo `theme` một lần. Nó dùng object đó cho nhãn của mình, đồng thời truyền chính object đó khi mở Settings.

```d2 interactive=false title="Một state phục vụ nhiều UI"
direction: down
owner: "Module theme\nMột instance do shell tạo"
shell: "UI shell"
remote: "UI Settings"
owner -> shell: "Snapshot và thông báo"
owner -> remote: "Snapshot và thông báo"
```

Unmount Settings chỉ hủy listener và nút của Settings; biến `theme` vẫn tồn tại trong shell. Mở Settings lần nữa phải đọc theme hiện tại, không mặc định quay về sáng. Khi toàn runtime kết thúc, shell cũng cần dọn listener của mình; ở bài tập này nó sống cùng document.

Lưu các file `basic/` theo đúng tên trong bài. Từ thư mục chứa `basic/`, chạy:

```bash
python3 -m http.server 8080 --directory basic
```

Mở `http://localhost:8080`. Bấm **Shell chọn tối** trước khi mở Settings. Bấm **Mở Settings**: remote hiện theme tối ngay. Bấm nút trong remote: cả nhãn shell lẫn remote đổi sang sáng. Đóng remote, chọn tối ở shell rồi mở lại để kiểm tra state sống lâu hơn UI.

Các module đặt cạnh nhau để tập trung vào luồng giao tiếp. Import tương đối không minh họa tải remote, Module Federation hay pipeline deploy độc lập. Khi tách bundle, loader phải cung cấp đúng API đã thống nhất; thứ tự truyền và gọi hàm vẫn như trong ví dụ.

## Áp dụng sang dữ liệu Cart có gì khác

Theme có thể đổi ngay trong bộ nhớ. Giỏ hàng lại cần backend xác nhận. Module Cart vẫn có thể công bố API tương tự, nhưng đường thay đổi là `addItem`, `setQuantity` và bước đọc có thể ở trạng thái đang tải/lỗi.

Không thêm `setCart` tùy ý chỉ để mọi remote sửa cùng object. Catalog gửi yêu cầu; Cart owner cập nhật snapshot từ kết quả đã xác nhận; header và Cart UI đọc snapshot. Mỗi UI không tự tính lại nghiệp vụ bằng cách đếm event.

Thử trong demo có sẵn:

<ExampleRef example="mfe-cart" version="snapshot">Example: owner sống lâu hơn UI</ExampleRef>

Thêm một cốc, mở **Xem luồng giao tiếp**, ẩn Header và Cart Vue, thêm tiếp rồi chờ xong. Mount lại cả hai: dữ liệu vẫn còn và listener trở về 2. Đổi sang bản **Event-only (bản lỗi)** để thấy việc không đọc snapshot khi mount làm UI hiện dấu **—**. Demo chỉ giữ state trong bộ nhớ, không gọi backend và không mô phỏng logout.

## localStorage lưu lại nhưng không tự đồng bộ UI

Nếu muốn giữ theme qua reload, owner có thể đọc `localStorage` khi khởi tạo, kiểm tra giá trị rồi dùng làm snapshot đầu. Khi `setTheme` thành công, nó cập nhật memory, báo listener và lưu preference. Lỗi truy cập storage phải được xử lý theo chính sách; theme vẫn có thể hoạt động trong memory khi không lưu được.

Chỉ gọi `localStorage.setItem` không khiến hai remote cùng trang tự render lại. Event `storage` không báo lại document vừa ghi; với `localStorage`, nó báo các document khác cùng origin đủ điều kiện như tab khác. Tab nhận cần validate và gọi đường cập nhật owner, tránh ghi qua lại thành vòng lặp.

Giỏ hàng, quyền truy cập hoặc thông tin user không được coi là hợp lệ chỉ vì đọc được từ storage. Với dữ liệu backend, tải lại và kiểm tra scope hiện tại. Nếu persist draft, cần version cấu trúc, thời hạn và phạm vi user; không lưu token/thông tin thanh toán để tiện chia sẻ.

## Vòng đời cần quyết định trước khi dùng store chung

| Sự kiện | Phần phải dọn | Phần có thể giữ |
| --- | --- | --- |
| Đóng một remote | Listener, timer và DOM của instance | State mà UI khác còn cần |
| Reload | Runtime trong bộ nhớ mất | Preference đã lưu hợp lệ; dữ liệu backend được tải lại |
| Logout/đổi user | Dữ liệu riêng tư, request/subscription scope cũ | Theme public nếu chính sách cho phép |
| SSR xử lý người khác | Không dùng state user của request trước | Chỉ module/stateless code; state tạo theo request |

Trong ví dụ theme, mọi caller được phép yêu cầu `setTheme`. Với Cart, header có thể chỉ nhận API đọc; Catalog nhận API gửi command. Đây là phân chia trách nhiệm để dễ bảo trì, **không phải sandbox bảo mật** cho JavaScript cùng trang.

Hai remote tự tạo hai store vẫn là hai bản state dù cùng cài một package. Nếu một lần đổi reducer bắt mọi team sửa theo, hãy đưa API nhỏ trước store thay vì expose cả cấu trúc bên trong.

## Những lỗi cần thử

1. Chọn theme trước khi mở remote: app mới có đọc được hiện tại không?
2. Đóng/mở remote nhiều lần: một thay đổi có render nhiều lần do listener cũ không?
3. Giữ reference snapshot cũ rồi đổi theme: snapshot cũ có bị sửa theo không?
4. Với dữ liệu user: logout lúc request cũ đang chạy, response cũ có bị chặn không?

Đối với backend, thứ tự response còn cần scope/generation hoặc version do server công bố. Nếu optimistic update — hiển thị trước kết quả dự đoán — được dùng, để một owner điều phối dự đoán và rollback. Không để mỗi UI cộng/trừ một bản riêng.
