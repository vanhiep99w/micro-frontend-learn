Giả sử shop có shell — khung ứng dụng chứa menu và điều hướng — cùng catalog và cart. Team catalog muốn thêm bộ lọc sản phẩm rồi deploy riêng, thay vì yêu cầu shell và cart cùng build lại.

**Module Federation cho phép các ứng dụng được build riêng cung cấp và sử dụng module của nhau khi ứng dụng chạy.** Nhờ đó, shell có thể ghép catalog vào cùng giao diện mà không phải đóng gói code catalog trong mỗi lần build shell. Các build cũng có thể chia sẻ một số thư viện chung, như React, theo cấu hình.

## Module Federation nằm ở đâu trong kiến trúc

Trong shop giả định này, catalog công bố module trang sản phẩm. Shell tải module đó khi người dùng mở catalog, rồi hiển thị nó trong vùng nội dung của ứng dụng. Code trang sản phẩm đến từ bản build catalog, không phải bản build shell.

Mục đích là **dùng chung module giữa các build độc lập, tạo điều kiện để từng phần frontend release theo nhịp riêng**. Module có thể là component hoặc function; không bắt buộc là cả ứng dụng.

Module Federation lo phần kết nối và tải module. Shell vẫn chịu trách nhiệm ghép giao diện, điều hướng và xử lý khi catalog không tải được. Vì vậy, đây là một công cụ để triển khai micro-frontend, không phải toàn bộ kiến trúc micro-frontend.

### Khác package và code splitting

Vẫn với thay đổi “catalog thêm bộ lọc”, điểm khác nhau là:

| Cách tích hợp | Điều xảy ra khi catalog có code mới |
| --- | --- |
| npm package được đóng gói vào shell | Shell cần cập nhật package, build và deploy lại để dùng code mới |
| Code splitting trong cùng app | Code được tách thành file để tải khi cần, nhưng vẫn phải build và deploy bản app mới |
| Module Federation | Catalog có thể build và deploy riêng; shell tải module từ bản catalog được chọn |

Nói ngắn gọn: **code splitting giúp tải code muộn; Module Federation giúp lấy code từ một build khác**. Hai cơ chế có thể dùng cùng nhau.

Release riêng vẫn có điều kiện: API giữa shell và catalog phải tương thích, và shell phải tìm tới đúng bản catalog mới. Nếu URL bản catalog bị ghi cố định trong build shell, đổi URL đó vẫn có thể cần rebuild shell. Chi tiết nằm ở [Dynamic remotes](/docs/module-federation/dynamic-remotes).

### Vì sao không dùng cách khác

Không bắt buộc phải dùng Module Federation. Nó phù hợp khi bạn muốn đồng thời **build/deploy riêng, ghép module vào cùng trang và có cơ chế chia sẻ thư viện giữa các build**. Ví dụ, shell React render component từ catalog, còn team catalog vẫn có thể phát hành bộ lọc mới theo nhịp riêng, với các điều kiện tương thích đã nói ở trên.

npm package và code splitting đơn giản hơn, nhưng tự chúng không giải quyết việc lấy module từ một bản build được deploy riêng. Các cách tích hợp khác vẫn làm được điều đó, với đánh đổi khác:

| Cách khác | Khi nào phù hợp | Đánh đổi so với ghép module bằng federation |
| --- | --- | --- |
| iframe | Cần cách ly giao diện và môi trường chạy | Phải kết nối thêm routing, giao tiếp và layout giữa hai document |
| Điều hướng sang site khác | Mỗi domain có thể là một site riêng | Chuyển sang document khác thay vì ghép module trong cùng trang |
| Native ESM và loader riêng | Muốn tải module từ URL theo quy ước tự thiết kế | Phải tự thiết kế thêm cách tìm module, quản lý dependencies và tích hợp giữa các build |

Lý do chọn federation không phải vì chỉ nó mới làm được, mà vì **bundler/plugin đã cung cấp cơ chế công bố, tìm, tải và chia sẻ module giữa các build**. Bạn bớt phải tự xây phần kết nối đó, nhưng vẫn phải quản lý tương thích và lỗi runtime. Xem [So sánh cách tích hợp](/docs/cac-cach-tich-hop/so-sanh) nếu cần chọn phương án cho kiến trúc cụ thể.

### Khi nào nên chọn và khi nào không

Mình chọn Module Federation khi các team sở hữu những phần frontend rõ ràng, cần release riêng nhưng vẫn muốn ghép module trong cùng trải nghiệm người dùng.

Nếu chỉ cần dùng chung design system hoặc helper, npm package thường đơn giản hơn. Nếu chỉ muốn giảm lượng JavaScript tải ban đầu, hãy bắt đầu bằng code splitting. Không cần thêm federation khi chưa có nhu cầu kết nối các build riêng.

## Các khái niệm cần nắm

| Khái niệm | Hiểu qua ví dụ shop |
| --- | --- |
| **Host** | Bên sử dụng module từ build khác: shell tải trang sản phẩm |
| **Remote** | Bên cung cấp module: catalog công bố trang sản phẩm cho shell dùng |
| **Shared dependencies** | Thư viện mà các build có thể dùng chung theo cấu hình, thay vì mỗi bên luôn dùng một bản riêng |

Một ứng dụng có thể vừa là host vừa là remote. Bạn chưa cần nhớ container, share scope hay các tùy chọn plugin ở bước này; bài cơ chế sẽ giải thích chúng theo luồng tải thực tế.

<Callout type="warn" title="Build riêng chưa bảo đảm hoạt động độc lập">
  Hai bên vẫn phải thống nhất API và thư viện dùng chung, đồng thời có cách xử lý khi remote lỗi. Federation cũng không phải sandbox để chạy code không tin cậy.
</Callout>
