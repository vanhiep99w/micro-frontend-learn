Giả sử shell vừa tải được `remoteEntry.js` của catalog với status `200`, nhưng mở trang sản phẩm vẫn gặp `ChunkLoadError`. Nếu entry đã tải xong, tại sao module chưa dùng được? Vì entry chỉ mở đường tới container; runtime còn phải khởi tạo sharing, lấy factory, tải các chunk cần thiết và đánh giá module trước khi shell nhận được exports.

Bài này đi theo một request `import('catalog/ProductPage')` từ lúc webpack build shell đến lúc code catalog chạy trong browser. Khi hiểu từng mốc, bạn sẽ biết nên kiểm tra cấu hình, network, shared dependencies hay lifecycle UI, thay vì thử sửa mọi thứ cùng lúc.

<Callout type="info" title="Phạm vi và điều kiện đọc">
  Ví dụ dùng shop giả định gồm shell và catalog, với `webpack.container.ModuleFederationPlugin` tích hợp trong webpack 5 và remote dạng script container. Đây không phải cấu hình Module Federation cho Next.js của site docs này. Bạn nên biết JavaScript modules, Promise và code splitting; nếu chưa rõ host/remote, đọc [Module Federation](/docs/module-federation) trước.
</Callout>

## Hai build độc lập gặp nhau ở runtime

Với import nội bộ như `import('./ProductPage')`, webpack biết implementation nằm trong dependency graph của build hiện tại. Với federated import, host chỉ biết một public request và cách tiếp cận remote. Implementation được compile bởi build catalog, rồi cung cấp qua container khi ứng dụng chạy.

```d2 title="Hai build độc lập gặp nhau ở runtime"
direction: right
hostbuild: Build shell
remotebuild: Build catalog
host: Shell runtime + remote reference
remote: Entry + chunks catalog
browser: "Gặp nhau trong browser"
hostbuild -> host -> browser
remotebuild -> remote -> browser
```

Điểm quan trọng không phải chỉ là code được tải muộn. Hai phía có artifact graph riêng: shell có thể được build hôm qua, còn catalog được build hôm nay. Khả năng ghép chúng phụ thuộc public contract và chính sách shared dependencies, không phải việc chúng cùng dùng một repository.

### Remote tạo gì khi build

Phần cấu hình sau minh họa build catalog. Entry, loaders và thư mục output được lược bỏ để tập trung vào federation:

```js title="catalog/webpack.config.cjs — phần cấu hình liên quan"
const { ModuleFederationPlugin } = require('webpack').container;

module.exports = {
  output: {
    uniqueName: 'shop_catalog',
    publicPath: 'auto',
    chunkFilename: '[name].[contenthash].js',
  },
  plugins: [
    new ModuleFederationPlugin({
      name: 'catalog',
      filename: 'remoteEntry.js',
      exposes: {
        './ProductPage': './src/product-page.js',
      },
    }),
  ],
};
```

Webpack tạo container entry chứa giao diện truy cập các exposed modules và phần runtime liên quan. Implementation của `product-page.js` cùng dependencies có thể nằm trong những chunk khác. Cách chia chunk phụ thuộc toàn bộ cấu hình build, nên không thể suy ra số file chỉ từ một exposed key.

`exposes` là bảng ánh xạ public key sang module nội bộ. Remote không mở toàn bộ cây source cho host: biết đường dẫn `src/internal-price.js` không có nghĩa host được phép lấy module đó qua container.

### Host biết gì khi build

Shell khai báo nơi tìm container:

```js title="shell/webpack.config.cjs — phần cấu hình liên quan"
const { ModuleFederationPlugin } = require('webpack').container;

module.exports = {
  output: {
    uniqueName: 'shop_shell',
  },
  plugins: [
    new ModuleFederationPlugin({
      name: 'shell',
      remotes: {
        catalog: 'catalog@https://assets.example.com/catalog/r17/remoteEntry.js',
      },
    }),
  ],
};
```

Khi gặp `import('catalog/ProductPage')`, webpack nhận ra `catalog` là remote alias, không phải npm package hay thư mục local. Nó sinh code để resolve container và lấy public key `./ProductPage`. Nó không tải source catalog về để compile chung với shell.

URL `r17` trong ví dụ được chốt khi build host, nhưng code catalog vẫn tải ở runtime. Muốn host chọn `r18` mà không rebuild cần một cơ chế chọn remote khác; đó là phạm vi của [Dynamic remotes](/docs/module-federation/dynamic-remotes).

## Remote entry và container là hai thứ khác nhau

Tên gọi dễ khiến bạn tưởng đây là hai file khác nhau. Thực ra, trong ví dụ webpack script remote ở trên, **remote entry là một file JavaScript; container là một object JavaScript mà file đó công bố khi chạy**.

Cụ thể với catalog:

1. Build catalog tạo file `remoteEntry.js`, rồi bạn deploy file đó cùng các chunk của catalog lên CDN.
2. Browser tải và chạy `remoteEntry.js`. Code trong file công bố object có tên `catalog`, để host truy cập qua `window.catalog`.
3. Host dùng object đó để yêu cầu module `./ProductPage`. Object này chính là **container**; nó có hai hàm chính là `init` và `get`.

| | Remote entry | Container |
| --- | --- | --- |
| Trong ví dụ | File `remoteEntry.js` trên CDN | Object `window.catalog` trong browser |
| Vai trò | Chứa code để thiết lập điểm truy cập tới remote | Cung cấp các hàm để khởi tạo sharing và lấy module |
| Bạn quan sát ở đâu? | Request file trong Network panel | Object và các hàm của nó trong môi trường JavaScript đang chạy |

Vì vậy, host **tải file entry**, rồi **gọi hàm trên container**. Container không phải component `ProductPage`, cũng không phải một Docker container.

```d2 title="Remote entry và container là hai thứ khác nhau"
direction: right
entry: remoteEntry.js
container: Container catalog
factory: Factory
entry -> container: "Tải và thực thi"
container -> factory: "get('./ProductPage')"
```

Trong sơ đồ, `get('./ProductPage')` trả về một *factory* — hàm để lấy exports của module, chưa phải component để render. Phần Container API ngay dưới sẽ tách rõ hai bước này.

Tên file `remoteEntry.js` đến từ cấu hình `filename`; tên object `catalog` đến từ cấu hình container `name`. Đổi tên file không tự đổi tên container. Remote dạng ESM hoặc integration khác có thể công bố container theo cách khác; `window.catalog` chỉ áp dụng cho mô hình script remote đang xét.

### Ba tên cần phân biệt

| Tên | Ví dụ | Dùng để làm gì |
| --- | --- | --- |
| Alias trong host | Key `catalog` của `remotes` | Prefix của `catalog/ProductPage` |
| Tên container remote | `name: 'catalog'`, phần trước `@` | Tìm container sau khi script chạy |
| Public module key | `./ProductPage` | Chọn exposed module trong container |

Alias và container name đang giống nhau để dễ đọc, nhưng không bắt buộc. Nếu host dùng `products: 'catalog@https://…/remoteEntry.js'`, import sẽ là `products/ProductPage`, còn global container vẫn là `catalog`.

`output.uniqueName` lại có nhiệm vụ khác: phân biệt runtime/chunk loading của các build cùng xuất hiện trên trang. Đặt container name đúng chưa đủ nếu hai build vẫn dùng cùng runtime name và gây collision.

### Container API

Container có hai hàm chính:

| API | Nhận gì | Ý nghĩa |
| --- | --- | --- |
| `container.init(shareScope)` | Bảng thông tin thư viện dùng chung, gọi là share scope | Kết nối cơ chế chia sẻ thư viện giữa host và remote |
| `container.get('./ProductPage')` | Tên module mà remote đã công bố | Tải các chunk cần thiết và trả về factory để lấy module |

`get` chưa trả thẳng component. Bạn nhận một hàm factory, gọi hàm đó mới có exports của module:

```js title="Sau khi container đã được khởi tạo sharing"
const factory = await container.get('./ProductPage');
const moduleExports = factory();
const ProductPage = moduleExports.default;
```

Đoạn này giả sử module có default export là component. `factory` là hàm **do `get` trả về**, không phải method thứ ba của container. Gọi factory chỉ lấy exports; nó chưa render component hay gọi `mount`.

`init` và `get` có thể được gọi với `await`, kể cả khi một nhánh hoàn tất đồng bộ. Factory trong mô hình này được gọi đồng bộ. Khi bạn viết `import('catalog/ProductPage')`, webpack xử lý các bước đó; không cần tự gọi lại trong component.

## Theo dõi một federated import

Luồng dưới đây mô tả lần đầu shell cần module catalog. Runtime có thể preload, dùng cache hoặc xen kẽ việc tải và khởi tạo; đây là các mốc logic, không phải cam kết thứ tự tuyệt đối của từng network request.

| Mốc | Chủ thể chính | Kết quả cần có trước khi đi tiếp |
| --- | --- | --- |
| Resolve remote | Host runtime | Container location tương ứng alias |
| Load entry | Script loader và browser | Container xuất hiện sau khi entry chạy |
| Initialize sharing | Host và remote runtimes | Các build tham gia cùng share scope |
| Get module | Remote container | Factory của exposed key; chunk cần thiết đã sẵn sàng |
| Evaluate | JavaScript runtime | Exports của module |
| Integrate | Shell | Component được render hoặc public API được gọi |

### Tải và thực thi remote entry

Với `remotes` tĩnh dạng `name@url`, webpack sinh script-loading code. Bạn không cần tự thêm một script tag khác vào component để “kích hoạt” remote. Runtime chờ script load và tìm container đúng tên.

Browser tải file và thực thi nó trong môi trường của document host. `200 OK` chỉ nói về HTTP response: response vẫn có thể là trang HTML fallback, JavaScript bị lỗi cú pháp, hoặc script không công bố container mà host đang tìm.

Nếu đã có container phù hợp trong runtime hiện tại, đường đi có thể tái sử dụng nó thay vì tải lại entry. Vì thế khi đọc Network panel, đừng mặc định mỗi federated import phải tạo một request `remoteEntry.js` mới.

### Khởi tạo share scope

Host runtime khởi tạo scope, mặc định tên `default`, rồi truyền object đó cho container. Trong webpack, các API tương ứng là `__webpack_init_sharing__('default')`, `__webpack_share_scopes__.default` và `container.init(scope)`.

Container tham gia scope bằng cách đăng ký các shared modules mà build của nó cung cấp và nối sharing tới remotes liên quan. Nếu catalog cũng consume remote khác, việc khởi tạo có thể lan tới container đó; runtime có cơ chế bảo vệ quá trình init khi graph chứa vòng lặp. Điều này không có nghĩa circular dependencies ở code ứng dụng trở nên dễ thiết kế hay không còn lỗi evaluation.

Khởi tạo scope không phải “tải hết mọi dependency” và cũng chưa đảm bảo mọi version hợp lệ. Việc chọn provider và kiểm tra version còn diễn ra khi shared module được consume. Một lỗi version vì thế có thể lộ ra trong quá trình lấy hoặc đánh giá module, không nhất thiết ngay tại `init`.

### Lấy module factory và tải chunk

Runtime gọi `container.get('./ProductPage')`. Container tra mapping do `exposes` tạo ra, tải những chunk cần thiết rồi trả factory cho exposed module.

Nếu public key không tồn tại, request này không tự rơi về một file có tên gần giống. Nếu chunk bị mất hoặc tải sai URL, Promise có thể reject dù entry đã tải thành công.

Với ví dụ catalog, bạn có thể thấy entry, chunk của `ProductPage` và một vendor chunk. Nhưng build khác có thể gộp hoặc tách chúng khác đi; đừng viết kiểm thử dựa vào giả định “mỗi expose đúng một request”.

### Đánh giá module rồi trả exports

Có factory chưa đồng nghĩa toàn bộ top-level code của exposed module đã chạy. Runtime gọi factory để lấy module; lúc này webpack thực thi module chưa được đánh giá và các dependency cần thiết theo quy tắc của nó, hoặc trả kết quả đã cache.

Nếu `product-page.js` có `console.log` ở top level, log đó xuất hiện khi module được đánh giá lần đầu. Nếu top level ném exception, federated import thất bại ngay cả khi các file đều đã tải xong.

Trong đường container API đang xét, loading là bất đồng bộ, còn gọi factory để đánh giá module là đồng bộ. `import('catalog/ProductPage')` bọc quá trình này trong Promise và resolve thành module exports. Những `import()` khác do remote gọi về sau vẫn có thể tạo các lượt tải bất đồng bộ riêng.

### Shell tích hợp public API

Sau khi import resolve, shell mới có thứ để dùng: `module.default`, `module.mount` hoặc exports khác theo contract. Federation runtime không tự gọi `mount`, không chọn DOM root và không quyết định remote nằm ở route nào.

Nếu export là React component, render thuộc trách nhiệm của React và shell. Nếu export là `mount`, shell gọi nó theo lifecycle contract. Cả hai đều diễn ra sau module resolution, nên “module loaded” và “UI usable” cần là hai mốc riêng khi đo trải nghiệm.

## Nhìn luồng qua container API

Đoạn sau mở phần plumbing để bạn đọc cơ chế. Nó chỉ minh họa đường gọi thủ công trong **code host đã được webpack compile**, sau khi script entry của remote đã chạy và cung cấp `window.catalog`.

```js title="Minh họa container API, không phải loader production"
async function readProductPageFromLoadedContainer() {
  // Các identifier này do webpack hỗ trợ trong bundle host.
  await __webpack_init_sharing__('default');

  const container = window.catalog;
  if (!container || typeof container.get !== 'function') {
    throw new Error('Catalog container chưa sẵn sàng');
  }

  await container.init(__webpack_share_scopes__.default);
  const factory = await container.get('./ProductPage');
  const moduleExports = factory();

  return moduleExports;
}
```

Đây không phải JavaScript để paste nguyên vào DevTools console: các identifier webpack không mặc nhiên là thuộc tính global của browser. Đoạn này cũng không tải entry, không quản lý concurrency, không timeout và không thực hiện policy chọn artifact.

Khi dùng `remotes` thông thường, hãy để webpack xử lý plumbing và viết `await import('catalog/ProductPage')`. Đường gọi thủ công là cách nhìn API, không phải bước bổ sung phải chạy trước mỗi import.

<Callout type="warn" title="Đừng trộn hai loader cho cùng một container">
  Tự chèn lại entry hoặc tự gọi `init` bên cạnh đường import do webpack quản lý dễ tạo race và khởi tạo trùng. Container giữ object scope đã nhận; gọi lại bằng một object scope khác có thể gây lỗi “already been initialized with a different share scope”. Nếu viết dynamic loader, cần tái sử dụng entry/container và Promise khởi tạo theo cùng định danh remote, không dùng `catch` rỗng để bỏ qua mọi lỗi init.
</Callout>

## Ví dụ tách tải module khỏi mount UI

Để nhìn rõ ranh giới, ví dụ này expose một lifecycle API dùng DOM thuần thay vì React component. Tên public vẫn là `./ProductPage`; contract gồm named export `mount(root, options)` trả về cleanup function. Tên module không quyết định hình dạng exports.

Các snippet là minh họa cho hai app webpack đã có entry và HTML, không phải project scaffold đầy đủ. Ví dụ không cần shared framework dependency; khi đổi sang component React trong cùng cây render, bạn cần thiết kế shared policy phù hợp ở cả hai build.

### Catalog expose một lifecycle API

```js title="catalog/src/product-page.js"
console.log('[catalog] ProductPage module evaluated');

export function mount(root, { onSelect }) {
  const section = document.createElement('section');
  const button = document.createElement('button');
  button.type = 'button';
  button.textContent = 'Xem sản phẩm minh họa';

  const handleClick = () => onSelect('demo-product');
  button.addEventListener('click', handleClick);
  section.append(button);
  root.append(section);

  return function unmount() {
    button.removeEventListener('click', handleClick);
    section.remove();
  };
}
```

Top-level log thuộc module evaluation. DOM chỉ được tạo khi host gọi `mount`, còn cleanup chỉ chạy khi host gọi hàm trả về. Federation không tự thực hiện hai thao tác sau.

`root` dành riêng cho catalog; callback `onSelect` là capability shell truyền vào. Remote không cần import router nội bộ của shell để báo người dùng chọn sản phẩm.

### Shell tải rồi mount

```js title="shell/src/open-catalog.js"
export async function openCatalog(root, onSelect) {
  let phase = 'load-module';

  try {
    const catalogModule = await import('catalog/ProductPage');
    phase = 'validate-contract';

    if (typeof catalogModule.mount !== 'function') {
      throw new Error('Catalog không cung cấp mount theo contract');
    }

    phase = 'mount';
    const unmount = catalogModule.mount(root, { onSelect });
    return unmount;
  } catch (error) {
    // Minh họa telemetry; production nên thêm build IDs và correlation ID.
    console.error('[shell] Catalog failed', { phase, error });
    root.textContent = 'Catalog chưa sẵn sàng. Bạn vẫn có thể dùng navigation.';
    return () => root.replaceChildren();
  }
}
```

Shell gọi `openCatalog` khi route cần domain này, chờ cleanup rồi lưu nó để gọi lúc rời route. Host thật cũng phải xử lý trường hợp route đã đổi trong lúc Promise còn pending: không mount kết quả tải muộn vào một view đã bị bỏ, và không để hai lần mở route tạo hai instance ngoài ý muốn.

Kiểm tra `typeof mount` chỉ xác nhận hình dạng tối thiểu, không chứng minh semantics hay toàn bộ input/output đúng contract. Tương tự, `try/catch` này bắt load rejection và lỗi mount đồng bộ, không bắt mọi exception trong event handler hoặc Promise do remote tạo sau đó.

Ở đây phase `load-module` gộp entry, init, get và evaluation vì `import()` là một Promise bên ngoài. Muốn phân biệt chính xác các phase bên trong cần thêm dấu vết Network, error cause hoặc instrumentation của runtime đang dùng; không suy ra phase chỉ từ dòng `await`.

### Async boundary ở entry của host

Một cách bootstrap thường dùng trong webpack là để entry tải module khởi tạo ứng dụng bằng dynamic import:

```js title="shell/src/index.js"
import('./bootstrap').catch((error) => {
  console.error('[shell] Bootstrap failed', error);
});
```

```js title="shell/src/bootstrap.js"
import { openCatalog } from './open-catalog';

const root = document.querySelector('#catalog-root');
if (!root) throw new Error('Thiếu catalog-root trong HTML của shell');

// Demo mở catalog ngay; app thật gọi theo route và lưu cleanup.
const cleanup = await openCatalog(root, (productId) => {
  console.log('[shell] Selected product', productId);
});

// Khi shell rời route, gọi cleanup().
```

Async bootstrap boundary đặc biệt hữu ích khi code khởi tạo app consume shared dependencies: runtime có cơ hội hoàn tất phần tải/khởi tạo cần thiết trước khi app dùng chúng. Nó không bắt buộc preload mọi remote.

Nếu gặp “Shared module is not available for eager consumption”, mình kiểm tra entry và async boundary trước. Bật `eager: true` cho mọi thư viện có thể khiến provided/fallback modules được tải sớm và phình initial payload; đó là thay đổi loading policy, không phải cách sửa mọi lỗi thứ tự khởi tạo.

## Share scope trao đổi điều gì

Bạn có thể hình dung share scope là bảng đăng ký providers theo shared key và version. Host và remote đưa thông tin cung cấp vào bảng; code consume chọn provider theo policy của build đó.

```d2 title="Share scope trao đổi điều gì"
direction: right
host: Host providers
catalog: Catalog providers
scope: "Share scope: default"
consumer: Shared dependency consumer
host -> scope
catalog -> scope -> consumer
```

Các entries chứa thông tin runtime để lấy module, không chỉ chuỗi version. Tên scope giống nhau là điều kiện cấu hình; khi init container, object scope thực tế cũng phải nhất quán. Tạo hai object riêng đều gọi là “default” không khiến chúng trở thành cùng scope.

Không có quy tắc tổng quát “host luôn thắng”. Provider được dùng phụ thuộc key, scope, versions, `requiredVersion`, `singleton`, fallback và trạng thái đã consume. Đặc biệt, một shared version đã được dùng không thể được thay nóng an toàn chỉ vì remote đến sau cung cấp version mới hơn.

`init` là bước kết nối sharing, không phải chứng nhận tương thích của mọi dependency. Nó cũng không nối state nghiệp vụ: hai build cùng dùng code của một thư viện store vẫn có thể tạo hai store instance khác nhau. Chi tiết các sharing hints và chiến lược React nằm ở [Shared dependencies](/docs/module-federation/shared-dependencies).

## Cache và vòng đời trong một document

Sau lần tải đầu tiên, nhiều thao tác không cần lặp lại. Nhưng từ “cache” ở đây có nhiều tầng; trộn chúng sẽ dẫn tới kỳ vọng sai khi test deploy hoặc rollback.

### HTTP cache khác module cache

| Tầng | Giữ gì | Điều nó không làm |
| --- | --- | --- |
| Browser/CDN HTTP cache | Response của entry, chunk và assets theo HTTP policy | Không quyết định React/DOM instance nào được tạo |
| Container và chunk-loading state | Container đã có, chunk đã tải và trạng thái/Promise trong runtime | Không tự dọn UI khi route đổi |
| Webpack module cache | Kết quả module evaluation trong runtime tương ứng | Không biến mọi lần gọi hàm tạo instance thành cùng một instance |
| Application state | Root, subscriptions, store/query client theo owner | Không được federation tự cleanup |

DevTools “Disable cache” chủ yếu tác động HTTP cache khi công cụ đang mở. Nó không xóa module đã được đánh giá trong document hiện tại. Reload tạo document/runtime mới, còn entry response mới hay cũ vẫn phụ thuộc network, HTTP policy và có thể cả service worker của app.

### Import lại không đồng nghĩa chạy lại module

Trong cùng runtime và cùng module identity, import thành công lần hai thường dùng module đã đánh giá, không chạy lại top-level code. Với demo trên, mở catalog, cleanup rồi mở lại thường chỉ log “module evaluated” một lần, nhưng tạo DOM mới ở mỗi lần gọi `mount`.

```d2 title="Import lại không đồng nghĩa chạy lại module"
direction: right
first: "Import lần đầu"
eval: Load / evaluate
exports: Exports
mountA: Mount A
later: "Import lần sau"
cache: Cached exports
mountB: Mount B
first -> eval -> exports -> mountA
later -> cache -> mountB
exports -> cache: "Được cache"
```

Vì vậy unmount UI không unload module khỏi webpack. Nếu remote tạo listener hoặc timer ở top level, cleanup của component không tự biết tới chúng. Mình ưu tiên tạo resources theo instance trong `mount` và dọn chúng qua cleanup, tránh dùng top-level side effects để quản lý lifecycle màn hình.

Nhận định cache này áp dụng cho cùng runtime/module identity. Hai runtime độc lập hoặc hai bản dependency được bundle riêng vẫn có thể đánh giá code nhiều lần. Không nên dùng một top-level biến làm bằng chứng rằng “toàn bộ trang chỉ có đúng một instance”.

### Deploy remote mới không thay code của tab cũ

Giả sử document đã tải catalog `r17`; server sau đó chọn `r18` cho người dùng mới. Module `r17` đã đánh giá vẫn tồn tại trong tab cũ. Import cùng request trong tab đó không tự lấy implementation mới chỉ vì file trên server đổi.

Nếu tab cũ chưa tải một lazy chunk của `r17`, nó vẫn có thể cần chunk đó khi người dùng mở chức năng khác. Xóa artifacts cũ ngay sau deploy khiến tab đang mở lỗi dù bản release mới hoàn toàn tốt.

Mình mặc định giữ artifact graph bất biến theo release và một lựa chọn remote nhất quán cho mỗi document. Muốn nâng remote giữa phiên phải thiết kế riêng cho container identity, module cache, shared versions, UI instances và state; đổi URL không đủ để biến đó thành hot swap an toàn.

## Tại sao entry tải được nhưng chunk vẫn lỗi

Entry là điểm vào một graph, không phải bằng chứng rằng cả graph dùng được. Một tình huống giả định:

```text
Entry mong muốn: https://assets.example.com/catalog/r17/remoteEntry.js
Chunk đúng:      https://assets.example.com/catalog/r17/731.a1b2.js
Chunk tải nhầm:  https://shop.example.com/731.a1b2.js
```

Nếu remote tạo chunk URL theo base của shell thay vì nơi lưu artifacts catalog, entry có thể `200` nhưng chunk bị `404`. `output.publicPath: 'auto'` giúp webpack suy ra base trong nhiều script-loading setup; bạn vẫn phải kiểm tra URL thực tế nếu dùng proxy, CDN hoặc topology khác.

Các nguyên nhân cần tách biệt:

- **Sai base URL:** chunk được tìm ở origin/path không thuộc release catalog.
- **Deploy không đồng bộ:** entry mới xuất hiện trước khi chunks của nó được publish đầy đủ.
- **Artifact cũ bị xóa:** entry hoặc tab cũ vẫn tham chiếu chunk đã mất.
- **Runtime collision:** hai build dùng cùng `output.uniqueName` hoặc container names xung đột.
- **Asset pipeline khác:** CSS, font hoặc ảnh cần thêm rules và URL policy riêng; chunk JavaScript tải được chưa đảm bảo mọi assets tải được.

Với script remote, tải cross-origin không có nghĩa mọi lỗi đều là CORS. Classic script loading, ESM, `fetch` manifest, CSS/font và API requests có yêu cầu browser khác nhau. Hãy đọc request type và lỗi cụ thể; CSP hoặc MIME sai cũng có thể chặn code.

Mình kiểm tra URL chunk và Initiator trước khi sửa `publicPath`. Nếu URL đúng nhưng artifact thiếu, đổi base URL chỉ che khuất lỗi publish hoặc retention.

## Chẩn đoán lỗi theo từng giai đoạn

| Giai đoạn | Dấu hiệu thường gặp | Kiểm tra trước |
| --- | --- | --- |
| Resolve/load entry | `ScriptExternalLoadError`, entry không tải được hoặc container missing | Alias, container name, URL, status/body, CSP và remote format |
| Initialize sharing | “already been initialized with a different share scope” | Có loader thứ hai, script bị chèn lại hoặc object scope không nhất quán không |
| Get exposed module | “Module … does not exist in container” | Public key có `./`, đúng hoa/thường và đúng release đã deploy không |
| Load dependent chunk | `ChunkLoadError` | URL thực tế, response body, `publicPath`, artifact retention và deploy graph |
| Consume shared dependency | Version mismatch hoặc eager-consumption error | Scope/key, version policy, async bootstrap và thời điểm consume |
| Evaluate module | Exception trước khi import resolve | Stack trace và top-level code của exposed module/dependencies |
| Integrate UI | Import resolve nhưng export không đúng hoặc mount/render lỗi | Export shape, input contract, framework compatibility và shell boundary |
| Run domain behavior | UI hiện nhưng tương tác/API lỗi | Lifecycle, event handlers, domain API và business state |

Thông điệp cụ thể có thể khác theo webpack/plugin version. Bảng là hướng tìm nguyên nhân, không phải parser phân loại lỗi theo string. Một Promise reject từ `import()` có thể bọc lỗi ở nhiều mốc bên trong.

Khi gửi telemetry, ghi ít nhất host build, remote build nếu xác định được, remote alias, exposed key, phase quan sát được và error cause. Nếu entry chưa chạy, có thể bạn chỉ biết release dự kiến từ config chứ chưa xác nhận build thực tế; nên phân biệt hai thông tin đó. Không gửi token hoặc query nhạy cảm trong URL.

Retry chỉ hữu ích khi nguyên nhân có khả năng tạm thời và loader cho phép phục hồi. Missing public key hoặc version mismatch cố định không được chữa bằng retry liên tục. Ngay cả với lỗi network, không giả định gọi lại cùng `import()` luôn tạo request mới: runtime có thể giữ trạng thái lỗi; cần kiểm chứng hành vi loader cụ thể và cung cấp đường reload khi cần.

<Callout type="warn" title="Load boundary không thay thế UI boundary">
  Bắt Promise reject của federated import bảo vệ đường tải module. React Error Boundary, nếu dùng React, bảo vệ một phần lỗi render/lifecycle của cây UI, không tự bắt mọi lỗi event handler hay async task. Shell cần loading/fallback và lifecycle policy riêng; federation không cung cấp chúng chỉ bằng khai báo `remotes`.
</Callout>

## Giới hạn của cơ chế

Module Federation nối modules giữa các build; nó không cung cấp sandbox. Script catalog chạy trong document shell với quyền JavaScript tương ứng của trang, có thể truy cập DOM và những tài nguyên origin cho phép. Một remote khác origin không có nghĩa nó được cách ly như iframe khác origin.

Cơ chế này cũng không tự giải quyết các ranh giới sau:

- Public exports tải được không chứng minh contract tương thích; types lúc build không validate implementation vừa deploy.
- Dependency singleton không đảm bảo CSS isolation, route ownership hay dùng chung state instance.
- Cleanup của UI không xóa module cache hoặc thay thế shared modules đã consume.
- Luồng browser script container không chứng minh cùng cấu hình hoạt động với SSR, hydration hoặc React Server Components.
- Một container có thể consume container khác, nhưng chuỗi phụ thuộc đó tăng failure paths và coupling vận hành.

Nếu bạn chỉ cần tải muộn code thuộc cùng một release, dynamic import local thường đủ. Chọn federation khi thực sự cần boundary giữa các build và sẵn sàng quản lý contract cùng artifact lifecycle; không chọn chỉ để biến mọi module thành network dependency.

## Bài tập quan sát runtime

Thực hiện trên hai app webpack thử nghiệm của bạn, không trên site docs này. Dùng demo DOM ở trên để tránh nhầm lỗi sharing React với lỗi loader.

1. **Quan sát lần tải đầu.** Mở document mới, vào catalog và xem Network theo cột Initiator. Tìm entry rồi các chunk cần thiết; ghi thời điểm log “module evaluated”. Số request không phải giá trị cố định.
2. **Phân biệt evaluation và mount.** Rời route, gọi cleanup rồi quay lại trong cùng document. Xác nhận DOM được tạo lại nhưng top-level log không xuất hiện lại cho module đã cache.
3. **Chặn entry.** Dùng request blocking, reload rồi mở catalog. Shell phải hiển thị fallback; các chức năng không phụ thuộc catalog vẫn dùng được.
4. **Chặn một chunk.** Xác định chunk cần khi lấy `ProductPage`, chặn nó rồi reload. Entry vẫn có thể tải thành công, nhưng import reject; kiểm tra phase và URL lỗi.
5. **Làm sai public key.** Trong bản test, import `catalog/UnknownPage`. Quan sát lỗi get/module mapping thay vì tìm một file `UnknownPage.js` trên CDN.
6. **Gây lỗi evaluation.** Trong bản test remote, thêm `throw new Error('demo evaluation failure')` ở top level. Phân biệt file tải xong với module đánh giá thành công; bỏ thay đổi sau khi test.
7. **Kiểm tra tab cũ.** Giữ tab đã tải `r17`, triển khai `r18` và mở tab mới theo config chọn release mới. Tab cũ không tự thay implementation. Nếu có lazy feature chưa mở, xác nhận chunks của release cũ vẫn tồn tại.

Với app dùng shared framework, thêm kiểm thử mismatch version và eager consumption theo policy đã chọn. Kết quả cần ghi lại là artifact nào được dùng, import thất bại ở đâu và shell còn usable thế nào, không chỉ “hai dev server nối được với nhau”.
